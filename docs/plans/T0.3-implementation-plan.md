# T0.3 implementation plan

> Frozen at the T0.3 gate close: every T0.3 acceptance criterion is checked in
> `MILESTONES.md`, with evidence indexed in
> `docs/qualification/T0.3-MANUAL-GATE.md`. This plan is history, not
> authority — `MILESTONES.md` owns status from here on.

## Outcome

Deliver T0.3 as small, green PRs that build one Ordo-owned GPUI foundation and
then consume it from two roots: the development-only `ui-lab` and the production
Preparation shell. Keep the current crate graph: `ui` owns reusable native
behavior and visual tokens; `ordo` owns application navigation and feature
composition; `platform` owns the small installation-preference filesystem
adapter. No domain or canonical-rendering behavior belongs in this task.

Every PR below ends with `cargo xtask verify`. UI PRs also add the smallest GPUI
harness check for the behavior introduced by that PR. T0.3's milestone
checkboxes remain open until the final acceptance PR proves the complete gate.

```text
                   |
                   v
PR 6  menus, selects, disclosures, and tabs
                   |
        +----------+-----------+
        v                      v
PR 7  editable Combobox    PR 8  shared scroll indicator
        |                      |
        +----------+-----------+
                   v
PR 9  one overlay layer: dialogs, slideovers, nested slideovers, toasts
                   |
                   v
PR 10 region navigation and AccessKit semantics
                   |
                   v
PR 11 production Preparation shell
                   |
                   v
PR 12 T0.3 acceptance and hardening
```

PRs 3 and 4 can be developed in parallel after PR 2, as can 7 and 8 after
PR 6. The rest are intentionally ordered: composite controls use the basic
control/focus contract; overlays use those controls; modal focus and focus
restoration must exist before global F6 navigation is finalized; the production
shell then consumes only proven `ui` Interfaces.

## Micro-PRs

### [DONE] PR 1 — Qualify the existing GPUI behavior dependency

**Depends on:** T0.1 and T0.2.

- Record, against the already pinned revisions, which `gpui-base` behaviors are
  adopted, wrapped, or rejected for the T0.3 primitive corpus. Include license,
  transitive dependency, keyboard/focus, AccessKit, and removal-seam evidence.
- Keep `gpui-base` private to `ui`; add verification that production crates do
  not depend on `gpui-component`, React, WebViews, CSS/Tailwind, or browser
  runtimes.
- Reuse the existing Cargo pin and `cargo deny` machinery. Add no dependency
  unless qualification proves a missing behavior that direct GPUI cannot cover;
  such an addition requires its own later qualification PR.

**Exit check:** the dependency graph and licenses are reproducibly checked, and
the chosen boundary is documented before more code depends on it.

### [DONE] PR 2 — Make `DESIGN.md` tokens and bundled operator assets executable

**Depends on:** PR 1.

- Expose the complete T0.3 semantic palette, typography, spacing, radii,
  borders, elevation, icon sizing, density, motion, focus, and supported scale
  values from `DESIGN.md` as typed values in `ui::tokens` rather than local
  literals. `DESIGN.md`'s YAML frontmatter is the single normative source and
  `ui::tokens` is its only machine-readable copy; `ui::tokens` tests pin every
  constant back to that frontmatter.
- Bundle the operator Atkinson Hyperlegible Next faces, Noto Sans fallback, and
  only the Lucide SVGs required by the T0.3 rail and primitives. Register assets
  in the offline runtime manifest and retain their license notices.
- Extend `xtask` checks for required assets and the one allowed icon family. Do
  not implement T0.4's canonical font cache, hash recovery, or renderer work
  here.

**Exit check:** a token/asset test detects drift or a missing bundled resource,
and no UI code needs a raw design literal.

**Amended:** T0.1's `crates/ui/design-tokens.json` was a validation fixture for
the verify harness, not a consumed artifact — its placeholder colors were never
in `DESIGN.md`'s palette. Expanding it would have made a third copy of every
token, checked against a fourth copy of hardcoded expectations in `xtask`. It is
deleted; `canonical_slide` moved into `ui::tokens`, and the runtime-manifest
check still exercises the same harness capability.

### [DONE] PR 3 — Add the UI environment: appearance, scale, and preferences

**Depends on:** PR 2.

**Amended:** PR 3 does not add a canonical-frame wrapper solely to test scale
isolation because no canonical-frame render path exists yet. Interface scale is
currently confined to operator spacing and typography. The invariant test moves
to T0.4 alongside the first canonical-frame consumer, where changing operator
scale can exercise and fail against real `1920x1080` geometry.

- Add typed `System | Light | Dark` Preparation appearance and
  `100 | 125 | 150 | 175 | 200` Interface scale state. Resolve System from
  GPUI's pinned window-appearance observer; Presenter resolves to graphite dark
  without overwriting the saved Preparation choice.
- Apply scale through operator typography/layout tokens, never a global window
  or canonical-frame scale. Add one canonical-frame viewport wrapper test that
  proves its internal `1920x1080` geometry is invariant across all five scales.
- Persist only these installation preferences through a minimal `platform`
  filesystem adapter using a temporary path in tests and the existing owned
  background-work boundary in production. Do not start SQLite or parish data
  persistence before T0.5.
- Register Settings and `Ctrl++`, `Ctrl+-`, `Ctrl+0` changes through the same
  state transition, including clamping at the supported endpoints.

**Exit check:** startup restore, live System changes, Presenter override/return,
shortcuts, and scale isolation are automated.

**Amended:** two exit-check items shipped without automation, for reasons that
outlive this PR.

*Scale isolation* had no canonical-frame render path to be isolated from — scale
reaches only operator typography and layout tokens, and T0.4 owns the renderer.
The wrapper written for it asserted that two constants were constants and could
not fail, so it and `CanonicalFrameViewport` were deleted rather than kept as a
green test proving nothing. The isolation proof belongs to T0.4, alongside the
composition it guards.

*Live System changes* are automated only as far as the pinned GPUI revision
allows: the `WindowAppearance` mapping and the `SystemAppearanceChanged`
transition are covered, but `TestAppContext::test_window` is `pub(crate)`, so
the `observe_window_appearance` wiring cannot be driven from a test. Recorded as
a pin property in `docs/qualification/GPUI-BASE-T0.3.md`, with T0.3's milestone
AC split so the live-following half is tagged `[MANUAL]` instead of claiming
automation it does not have.

### [DONE] PR 5 — Ship basic controls and the shared focus treatment

**Depends on:** PRs 3 and 4.

- Add Ordo-owned Button and Field Interfaces, icon/label handling, Disabled,
  Unavailable, Read-only, and Not-assigned presentation, and pointer tooltips.
- Centralize the two-layer keyboard-only focus treatment and High Contrast
  escape hatch; keep focus independent from selection and apply it outside a
  canonical-frame wrapper.
- Wrap only qualified `gpui-base` behavior. Public Ordo Interfaces expose typed
  state/actions, not `gpui-base` styling or properties.
- Add lab scenarios and tests for default, hover, pressed, focused, disabled,
  unavailable, read-only, long text, icon-only naming, and both appearances.

**Exit check:** Button and Field keyboard activation, labels/values/actions,
and tooltips are automated.

**Amended:** *focus modality* is automated only as far as the pin allows. The
Button applies the treatment through GPUI's own `focus_visible`, which resolves
keyboard modality; the Field's wrapper resolves it from
`Window::last_input_was_keyboard`, because the base input owns the focus handle
and `focus_visible` needs the styled element to track it. GPUI exposes no
computed style to a test, so what is asserted is `focus_rings` itself — two
layers, order, colors, and scale growth — and the `[MANUAL]` keyboard-only
check in T0.3 still owns the on-screen half.

*High Contrast* was dropped rather than shipped. The pinned GPUI reports no
such platform mode, and a GPU-composited window gets no system repaint of its
own controls, so there is no operating-system focus indication to hand back to:
the escape hatch only deleted Ordo's rings and left nothing. That also
contradicted this milestone's own `[MANUAL]` gate, which asks for the two-layer
treatment to be *preserved* under Windows High Contrast. Ordo paints it in
every mode, which DESIGN.md permits ("unless the complete Ordo focus treatment
replaces it"). Revisit when a GPUI revision reports the mode and its system
colors — that reruns the `gpui-base` qualification anyway. Windows is the
primary target; DESIGN.md's "or equivalent platform modes" would cover GNOME
High Contrast and macOS Increase Contrast on the same signal.

*Long text* is staged, not handled. The lab renders a long Cebuano label on a
Button, but Button applies none of DESIGN.md's truncation rules, so the control
simply widens; the lab row wraps, which hides the overflow at the row level
rather than at the control. Truncation policy is per-context (a title, a file
name, and a label do not shorten the same way) and belongs to the typography
and truncation work, not here — the scenario exists so that work has something
to fix.

*AccessKit* nodes are captured from the element rather than the window, because
the test platform never activates the tree; and a consequentially blocked
control announces itself through its description, because the pin exposes no
disabled flag. Both are recorded in `docs/qualification/GPUI-BASE-T0.3.md`.

### [DONE] PR 6 — Ship composite selection and navigation controls

**Depends on:** PR 5.

- Add Menu, Select, Disclosure, and Tabs on the same control and focus
  contracts. Preserve expected arrow-key behavior and visible reading order.
- Keep global destinations out of Tabs; tab semantics are only for local views.
- Add curated lab scenarios at every appearance/scale/viewport combination,
  including constrained menus and long multilingual values.

**Exit check:** keyboard-only open/select/close behavior, semantic role/state,
and focus return pass through each owning primitive Interface.

**Implementation:** `primitives::selection::{Menu, Select, Tabs}` and
`primitives::disclosure::Disclosure`, with caller-owned state and the shared
focus treatment. The Select commits on activation; local tabs
use manual activation so focus and selection stay independent. The lab and
primitive tests cover keyboard/pointer behavior, final AccessKit nodes, and
the 80 appearance/scale/viewport scenario combinations. See
`docs/qualification/GPUI-BASE-T0.3.md` for the pin's relationship/tree limits.

**Verification:** `cargo xtask verify` passes, including all 36 UI tests and
the dependency/advisory/license audit. The pointer-to-keyboard Unavailable
choice regression was observed failing before the shared focus fix.

**Amended:** what shipped as `Combobox` is a **Select** — a button trigger plus
a popup list, with no text entry and no filtering. The word was wrong in the
code and in three contracts at once, so the rename is not cosmetic: `DESIGN.md`
now defines both primitives and when each applies, `MILESTONES.md` and
`MVP-PLAN.md` list them separately, and
`docs/qualification/GPUI-BASE-T0.3.md` splits its table row and records that the
base package uses `Combobox` and `Select` interchangeably for the one behavior
both Ordo primitives wrap. The AccessKit role does not change; `ComboBox` is
correct for a collapsed select either way. The real editable Combobox that the
contracts still require becomes PR 7, and `MVP-PLAN.md`'s editable Presider and
Choir selectors are its first production callers.

Review also found the primitive's visible layer weaker than its behavior, and
those fixes land in this PR beside the rename: the popup was opening a full
control-height below its trigger because `Anchored` already anchors to the
trigger's bottom-left; the Select trigger painted a long value outside its own
box for want of `min_w_0`/`truncate`, and the Disclosure region overflowed the
window for the same missing `min_w_0`; popup choices had no hover treatment or
pointer cursor at all, so an executable row looked exactly like an inert
`Unavailable` one; `close()` returned focus to the trigger even on pointer
dismissal, which `DESIGN.md` asks for only when a *focused* surface closes; the
Select announced its value twice, once in the composed accessible name and again
in `aria_value`, which needs the visible label and the accessible name to become
separate seams on Button; `Disclosure::set_expanded` stole focus on a
programmatic collapse that the operator did not invoke; and `"Not assigned"` is
a bare literal with no caller override. The lab matrix proved only that popups
stay inside the window, which is why the 36px gap survived 80 combinations — it
gains a trigger-attachment assertion, with the snapped-popup case allowed for.

Two of those became seams on Button rather than local patches, because the
Select is only their first caller: `name()` separates the accessible name from
a visible label that carries more than identity, and `truncate()` is the
per-context truncation the typography work will reuse. Two were left alone on
purpose: the scroll indicator is PR 8, and `"Not assigned"` keeps a
`ponytail:` note until a caller needs another word. The Select trigger's
truncation carries one too — `debug_bounds` measures the box, not the glyphs,
so no test in this harness can see a label painting outside it.

### [DONE] PR 7 — Add the editable Combobox

**Depends on:** PR 6. Can run in parallel with PR 8.

- Compose the Combobox from the two primitives that already exist: an Ordo
  Field as the trigger and the Select's popup list, wrapping the same qualified
  base open/focus/dispatch behavior. Add no dependency and no third selection
  implementation.
- Typing filters the visible choices; Up/Down move the active choice without
  stealing the caret; Enter commits; Escape reverts to the committed value and
  returns focus to the field. Provisional arrow focus stays provisional, as in
  the Select.
- This breaks `selection.rs`'s "collections are fixed for the lifetime of their
  state" contract, because filtering changes the visible set. Rework the
  per-choice `Vec<FocusHandle>` indexing so a choice keeps its identity across
  filters rather than indexing the filtered view.
- Accepting a value outside the set belongs to its callers, not the primitive;
  `MVP-PLAN.md`'s quick-create Choir selector is T3.10's problem, and the
  primitive only needs to not prevent it.
- Add lab scenarios for filtering to one match, to none, and over long
  multilingual values, at both viewports and every scale.

**Exit check:** keyboard-only type/filter/commit/revert, caret-versus-active
independence, the final AccessKit node, and focus return are automated through
the Combobox Interface.

### [DONE] PR 8 — Add the shared scroll indicator

**Depends on:** PR 6. Can run in parallel with PR 7.

- The pinned GPUI scrolls without painting anything and ships no scrollbar
  element, so a list taller than its bounded owner gives no sign that more
  exists below the fold. Add one Ordo-owned thin overlay indicator drawn from
  `ScrollHandle::offset()` and content-versus-viewport height, per `DESIGN.md`.
- One shared implementation, applied by the surfaces that already scroll: the
  Select/Menu popup today, PR 9's overlay bodies next, and T0.4's Cue timeline
  and dense editor lists after that. Do not reimplement it per list, and do not
  reserve a layout gutter for it.
- It reports position, and may also be dragged: `DESIGN.md` requires only that
  it never be the *only* way to scroll. Wheel, keyboard, and existing scroll
  behavior stay unchanged, and the indicator is absent whenever the content
  fits. A bar thin enough to sit over content is too thin to aim at, so it
  widens when the pointer reaches for the edge and covers no more of the
  content than the moment requires.

**Exit check:** a scenario taller than its viewport shows the indicator and its
proportional position at every scale; the same content that fits shows none;
and the pointer can widen the indicator and drag the surface to the end of its
collection without that press dismissing the surface.

### [DONE] PR 9 — Own all temporary surfaces in one overlay layer

**Depends on:** PR 6.

- Add one application overlay host and typed Dialog, Slideover,
  nested-Slideover, and Toast requests. There is no second stacking system.
- Bound overlays to the window viewport with exterior gutters, fixed
  header/actions, and an internally scrolling body. A single dim scrim captures
  the first pointer event and prevents click-through.
- Trap modal focus and restore the invoker or nearest surviving target. Preserve
  parent state while a nested slideover is active.
- Implement interruptible `400ms` enter and `200ms` exit tokens; reduced motion
  removes spatial movement and caps clarifying opacity at `100ms`.
- Keep transient confirmation/Undo toasts bottom-center; persistent failures
  stay with an explicit owner.

**Exit check:** constrained nested-overlay scenarios prove containment, scroll,
scrim capture, Escape/outside-click order, interruption, reduced motion, and
focus restoration.

**Implementation:** `ui::overlay` owns the one layer. `OverlayHost` holds the
stack, `Overlay::dialog`/`Overlay::slideover` are the typed requests, and
`Toast::confirmation`/`Toast::failure` are the two kinds of bottom-center
message. `LabView` renders `OverlayHost::layer` once, last, and the `dialog`,
`slideover`, and `toasts` scenarios reach the same keyed host — the production
shell consumes it the same way in PR 11. See
`docs/qualification/GPUI-BASE-T0.3.md` for the base behavior adopted and the
three rows of its table this PR amends.

**Verification:** `cargo xtask verify` passes, including 68 UI tests. The
overlay matrix covers both surfaces at both appearances, five scales, and both
viewport presets, with the nested slideover opened and closed inside each.

**Amended:** three qualification rows changed under implementation, and one
milestone AC turned out to belong here rather than to PR 10.

*Dialog* is rejected as the modal root for both surfaces, and `Sheet` adopted
for both. The base `Dialog` writes a `Dialog` role onto a host div Ordo cannot
name, and `DESIGN.md` makes the name, the description, and the scrim Ordo's;
`Sheet` carries no role at all, so Ordo's own surface is the named node. What
`Dialog` had that `Sheet` does not is Enter-confirms and its own layering, and
neither is missed: `DESIGN.md` asks for no Enter-confirms — Enter on the focused
primary action is the standard path — and this host hands out its own deferred
priorities, which it has to anyway to keep a popup opened *inside* a body above
the surface that owns it.

*ToastStack* is rejected and `ToastManager` adopted. The stack element is
spring-driven and scales a collapsed stack, both of which `DESIGN.md` forbids;
the manager is pure bookkeeping — ordering, timeouts, same-id replacement, exit
coordination — and is what "stacking and transition bookkeeping" was worth.
Keying it by the message rather than a counter is what makes the channel
deduplicated, which `DESIGN.md` asks for in the same sentence.

*Motion* comes from `gpui_base::motion::transition`, which is the base's
duration-and-easing counterpart to the spring the qualification rejects. It
retargets from the value it is at, so an interrupted surface reverses rather
than jumping, and it collapses to its target under `App::reduce_motion` —
which is what removes the movement under reduced motion rather than merely
shortening it. It adopts its first target on the spot, so the frame that opens
a surface seeds the transition where the surface starts.

*The dialog's entrance* rises one spacing step into its fade and falls back
through it, rather than growing through a scale the way a web dialog does: the
pin has no transform on `Style` at all — only `svg` has one, and the base's own
effect vocabulary is slide, fade, width and height for that reason. A width and
height animation would be a real scale and would rewrap every line of the body
on every frame of it. The rise is a relative inset, so it moves nothing else,
and it rides the same `progress` as the fade on the same easing.

*Toast departure* is the arrival in reverse: a leaving toast takes the space
above it away as it fades, so the stack rides down over the exit rather than
dropping at the end of it.

*Toast motion* is the same rise as the dialog's, one control height, so a
toast arrives from below the bottom edge and falls back through it rather than
cutting in and out. The manager's exit duration is what keeps a leaving toast
mounted long enough to be seen leaving; its enter duration stays zero, because
a toast is present the moment it is posted.

*The stack itself* moves too: a toast the newcomer pushes up rides up rather
than being redrawn a row higher. That needs the newcomer's height, which no
token gives and which GPUI reports a frame late through
`on_children_prepainted`, so an unmeasured toast stays out of the flow for the
one frame it is measured on and joins the stack on the next.

*Amended after review (2).* A control on a leaving card is still hit-testable
— opacity gates neither the hit test nor a listener — so pressing the primary
twice ran the delete twice while `close` correctly refused the second call.
Both halves are now guarded together, in one place all three controls route
through: the primary, the secondary, and a toast's Undo.

*Amended after review.* An exit is motion, so it may not delay the next input:
focus goes back to the invoker when a surface starts leaving rather than when
it finishes, the leaving card stops occluding, and a surface that is not the
topmost open one keeps its shape but gives up the outside press and the pointer
capture. It is made inert rather than unwrapped because at this pin an
element's identity is its path, and moving the controls inside a surface loses
their keyed state and their focus handles with it. The dim moved to the layer,
one for the whole stack, so nesting does not deepen it. And the Tab walk now
ends on the surface itself when it gives up, rather than wherever the last step
left it.

*Pointer and wheel containment* were both missing from the first cut and are
one mechanism. `DESIGN.md` gives the scrim the pointer entirely, not only the
click, so a control it covers must not hover, must not lend a cursor, and must
not raise a tooltip; and GPUI's own wheel listener never stops propagating, so
a wheel over a popup inside a slideover body inside the workspace scrolled all
three at once. `occlude` settles both — on the scrim, and on every bounded
scrolling surface through the new `Scroll::bounded`, which the Select/Menu
popup adopts along with the overlay body. `DESIGN.md` gains a sentence for each,
because both were stated there only as far as the click.

*Tab containment* was listed under PR 10 with the rest of focus navigation, but
a modal that cannot hold Tab is not a modal, so the two focus-order keys land
here. GPUI binds neither, and the pin binds `tab` only inside a text input,
where a single-line Field propagates it straight back out. `ui::init` binds
them, and the overlay layer answers them by cycling inside its own trap: the
pin's `focus_trap` element registers the container and leaves the policy to the
styled façade this crate rejects. PR 10 adds `F6` and the region registry
beside them.

### [DONE] PR 11 — Replace the prototype with the Preparation shell

**Depends on:** PR 10.

- Move application workflow ownership out of `ui::RootView` into
  `crates/ordo/src/shell/`; `ui` retains only reusable primitives and scenarios.
- Build the vertical rail with Masses, Library, Themes, Transfer & Backup, and

**Exit check:** shell tests navigate every destination and local tab, verify

**Implementation:** `crates/ordo/src/shell/` owns `ShellView` and its rail;
`ui::RootView` is deleted rather than moved, and the shell actions go with it.
`ui` keeps only the actions it binds or answers. See the T0.3.11 section of
`docs/qualification/GPUI-BASE-T0.3.md`.

**Verification:** `cargo xtask verify` passes all nine gates, including 81 UI
tests and 11 `ordo` tests.

**Amended:** two `ui` Interfaces changed under implementation, both because
this is the first workspace to consume them.

*`RegionRegistry::render` is replaced by `region` plus `root`.* One call that
wrapped and placed every region could only produce siblings in a flat list, and
a workspace is not one: the rail, header, list, and editor are consecutive in
reading order but nested in layout. `region` wraps one in reading order and
hands it back to be placed; `root` hosts the handlers over what was wrapped and
has to be their ancestor.

*`RegionRegistry::focus_region` is new*, and is how a focused editor gives the
keyboard back. It waits for the next render, because `Window::focus_next` reads
the last rendered frame's tab stops and the caller is changing what is mounted
— the same task shape PR 8 uses. The invoker's own handle could not carry this:
`gpui_base::Button` takes its handle from `Window::use_keyed_state`, which does
not survive an unmount.

## Deliberate boundaries

- Do not build Presenter workspaces, Mass editor workflows, canonical rendering,
  pagination, virtualized slide grids, or parish storage in T0.3.
- Do not add a general theme engine, public component library, alternate shell,
  plugin system, or custom animation framework.
- Use GPUI's pinned appearance observation, accessibility, input, and animation
  facilities plus the already installed `gpui-base` behavior where qualified.
  Prefer direct GPUI when wrapping a base behavior would leak its API.
- Keep tests beside their owning Rust crate unless the existing workspace test
  layout gains a real cross-crate need; do not create another workspace package
  merely to mirror the illustrative `tests/ui/*` milestone paths.
