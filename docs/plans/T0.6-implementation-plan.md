# T0.6 implementation plan

> Active plan. `MILESTONES.md` owns T0.6's status and acceptance gates; this
> file owns only the order in which the work lands. Freeze it at the gate close.

## Outcome

Prove the Presenter hot path is a pure, deterministic Presentation Engine call
plus one paint, instrument it, and record the memory/latency baselines Phase 1
is gated on. One PR built from four work packages, each ending in
`cargo xtask verify`.

Constraints that shape the split:

- **`presentation` stays pure.** The xtask contract already forbids GPUI,
  SQLite, filesystem, and platform edges for `presentation`; Presenter
  navigation, Freeze, Blackout, and Space are added there as value-level
  commands over Cue indices, never over GPUI or storage handles.
- **`unsafe_code` is forbidden.** Process memory and CPU come from `sysinfo`
  (already in `Cargo.lock` transitively); GPU allocation counters are not
  exposed by the pinned GPUI snapshot, so the report records them as
  `Unavailable` rather than inventing a number.
- **Hardware acceleration** is read from `Window::gpu_specs()`
  (`is_software_emulated`); a software fallback is surfaced in Diagnostics and
  in the report, never silently chosen.
- **Retained path:** the pinned GPUI exposes `Window::paint_glyph` and
  `TextSystem::add_fonts`/`resolve_font`, so a `rendering::Frame` can be walked
  straight into the scene. Face fidelity is checked by comparing GPUI's glyph
  ids for the resolved bundled face with the canonical shaper's glyph ids.
- **Manual review** happens in the real app: the Diagnostics destination gains
  a Performance panel (live latency percentiles, memory, startup, renderer
  acceleration, display-path comparison) with a button that runs the 500-Cue,
  2,000-command bench in-process.

## Work packages

```text
WP1 presentation Presenter commands, coalescing, caches ─┐
WP2 ordo performance metrics + sampling ─────────────────┼─> WP4 integration: Diagnostics panel,
WP3 ordo display-path comparison + face resolution ──────┘   bench/E2E, xtask measure-presenter, CI
```

### WP1 — Presenter Engine (`crates/presentation/`, `tests/presentation/`)

- `presenter` module: `PresenterCommand {Next, Previous, GoTo(usize),
  TakeLive (Space), ToggleFreeze, ToggleBlackout}` over a `CueDeck` of `n`
  Cues; `PresenterState {preview, program, frozen, blackout, revision}`
  returned complete by `apply`. Freeze holds Program while Preview navigates;
  Blackout forces Program black while Preview navigates; Space while frozen or
  blacked out releases the hold and takes Preview live.
- `coalesce(&[PresenterCommand]) -> Vec<PresenterCommand>`: only runs of pure
  navigation collapse into one `GoTo`; Space/Freeze/Blackout are barriers.
  Property-style test: for random sequences the coalesced and raw sequences
  reach the same final state.
- `FrameCache`: byte-bounded LRU of full-resolution frames;
  `ThumbnailCache`: lower-resolution entries keyed by Cue, `retain_visible`
  releases everything outside the virtualized window.
- New `presentation-tests` crate at `tests/presentation/` (dev-deps only),
  registered in the workspace and in xtask's expected member list.

### WP2 — Performance instrumentation (`crates/ordo/src/performance/`)

- `LatencyHistogram` per `(CommandKind, Surface::{Preview, Program})` with
  p50/p95/p99; keydown timestamp captured in the action handler, paint
  timestamp in `Window::on_next_frame`.
- `FrameTimer`: frame times and dropped frames (frame > 2× refresh interval).
- `ProcessSampler` (sysinfo): RSS, private/virtual memory, idle CPU.
- `StartupClock`, `QueueLatency` (enqueue→dequeue for workers), GPU allocations
  `Unavailable`.
- `PerformanceReport` serializable to a stable text/JSON form.

### WP3 — Display-path comparison (`crates/ordo/src/performance/display_path.rs`)

- CPU path: `rendering::rasterize` → RGBA → PNG encode → decode → GPUI image;
  record latency and held bytes.
- Retained path: register bundled faces with `add_fonts`, paint the `Frame`'s
  placed glyphs with `paint_glyph`; record latency and held bytes (glyph-atlas
  estimate).
- `verify_bundled_faces`: the GPUI-resolved face's glyph ids match the
  canonical shaper's glyph ids for a probe string in both Atkinson
  Hyperlegible Next and Noto Sans.

### WP4 — Integration

- Hot-path wiring in `ordo`: Presenter actions call only the Engine and
  request one paint; a test-only probe asserts no worker send, file access, or
  canonical recomposition happens between keydown and paint.
- Diagnostics destination Performance panel + "Run Presenter bench" button.
- `tests/performance/` (`performance-tests`): 500-Cue fixture, 2,000 mixed
  commands, final state asserted against a pure Engine oracle, p95 < 50 ms,
  memory < 1 GiB ceiling and 512 MiB budget, three-run baselines.
- `cargo xtask measure-presenter` (`xtask/src/measure_presenter.rs`) runs it
  and writes `target/ordo-performance/report.json`; new mandatory
  `windows-presenter-performance` CI job.

## Manual review addendum (WP4)

What landed differently from the plan, so the manual reviewer reads the panel
with these limits in mind:

- **The bench is engine-only.** `run_presenter_bench` times
  `PresenterEngine::apply` from keydown to state-ready. Preview and Program are
  stamped from the same instant, because the engine returns both in one state.
  No window paint is inside the timed span. The keydown-to-paint AC therefore
  stays open until a live Presenter window exists.
- **No runtime hot-path probe.** A thread-local send counter was removed in
  review: the bench runs off the GPUI thread, so it could only ever read zero.
  Engine purity is enforced structurally by the xtask dependency contract; the
  runtime hot-path AC stays open until a live Presenter window exists.
- **Memory baselines are process RSS, not a shell.** The empty-shell phase is
  the bare test process. The Preparation phase is a 10,000-entry synthetic
  library. The Presenter phase adds a 500-Cue text deck and the bench's engine
  state. Each sample includes fixtures earlier phases left resident in the run.
- **Startup is first render, not first paint.** `StartupClock` records the first
  `ShellView` render, which precedes the first paint by one frame.
- **Frame timing, idle CPU, GPU allocations, and worker queue latency are not
  recorded** by the engine bench. The report leaves them empty or unavailable.
- **The display-path comparison is not shown in the running app.** It is
  test-only (`cargo test -p ordo display_path`). The panel says so.
- **Display-path numbers are test-platform only** (`NoopTextSystem`, no GPU)
  and the CPU path was measured in debug; neither is recorded. That AC stays
  open until a native window measures both paths and records the result. The
  face-resolution check does use native DirectWrite and stays ticked.
- **`[NATIVE-AUTO]` boxes stay open** until `windows-presenter-performance`
  passes in CI and the owner accepts the runner as minimum-profile hardware.

## Closing the open AC (WP5–WP7)

The engine-only spike left six AC open because no live Presenter window
existed. The owner chose to close them inside T0.6 with a native measurement
harness rather than defer them. The owner's AMD Radeon development machine
counts as minimum-profile hardware for now; CI's `windows-2022` runner is
recorded as-is (it may report a software adapter, which the report states
rather than hides).

Shaping constraints, checked against the pinned `gpui-pre 0.3.8` source:

- **A real window, not the test platform.** `gpui_platform::application()`
  opens native windows; the harness is `crates/ordo/examples/presenter-lab.rs`,
  launched as a separate release process per measurement so each memory
  baseline is a clean process.
- **Keydown → presented frame.** Synthetic keys enter through
  `Window::dispatch_keystroke`, so they take the real key-binding and action
  path. The keydown stamp is taken immediately before dispatch. Each surface's
  paint stamp is taken in its own `canvas` paint. The first paint in a drawn
  frame schedules a settle callback with `Window::on_next_frame`. In pinned
  GPUI that callback runs at the start of the next frame, before that frame's
  draw, so it sees the earlier frame already presented. Preview and Program are
  painted in the same frame, so each command records both surfaces from that
  one frame. The next key is dispatched only after the settle callback runs.
- **Frames.** A frame loop of `on_next_frame` re-arms itself during the run
  and feeds `FrameTimer`; dropped frames are intervals over 2× refresh.
- **Hot-path probe.** A GPUI-thread `hot_path` scope opens at keydown and
  closes at paint. Known off-path choke points (canonical worker sends,
  preference saves, the lab's thumbnail worker send, filesystem access in the
  lab) call `hot_path::note(kind)`; any note inside an open scope is a
  violation, counted and reported. A test proves a deliberate violation is
  caught, so the probe cannot only ever read zero.
- **Worker queue latency.** The lab owns one named thumbnail worker
  (`std::thread`, `async-channel`, explicit `Stop` on window close) that
  downscales Cue frames off the GPUI thread; each request is `Enqueued` and
  observed by `QueueLatency` on dequeue.
- **Idle CPU.** After the command run the lab idles for a fixed window with no
  input and samples process CPU over it with `ProcessSampler`.
- **Display paths natively.** A `--display-path` mode paints one canonical
  frame through the CPU raster path (rasterize → encode → decode → GPUI image)
  and through the retained `retained_frame` element in a real window, timing
  notify → presented frame for each and recording held bytes.
- **Memory baselines from the real app.** `--baseline empty|preparation|presenter`
  opens the real operator runtime (empty shell), the shell plus a synthetic
  10,000-entry library held in memory (Preparation stand-in; no Preparation UI
  exists yet), and the Presenter probe window with a 500-Cue deck. xtask runs
  each mode three times as fresh processes.

### WP5 — Live Presenter probe (`crates/ordo/src/performance/live.rs`, `hot_path.rs`)

Files: `performance/live.rs` (new), `performance/hot_path.rs` (new),
`performance/mod.rs`, `performance/report.rs`, `canonical_views.rs` and
`lib.rs` (only `hot_path::note` calls at send sites).

- `PresenterProbe` view: owns a `PresenterEngine` over an n-Cue deck, renders
  Preview and Program side by side (cue label + revision; Black/Frozen
  markers), binds Right/Left/Space/F/B to Presenter actions.
- Action handler: apply, open hot-path scope, `cx.notify()`, schedule
  `on_next_frame` that records Preview and Program latency into a
  `LatencyBook` and closes the scope.
- Self-driver: `drive(commands)` dispatches the 2,000-command seeded stream via
  `dispatch_keystroke`, one per presented frame; returns a `PerformanceReport`
  with `latency_scope = "keydown_to_paint"`, frames, worker queue, idle CPU,
  RSS, renderer (`gpu_specs`), hot-path violations.
- Report gains `hot_path_violations` in JSON and summary.

### WP6 — Native display-path comparison (`crates/ordo/src/performance/native_display_path.rs`)

- A view that alternately shows the CPU-path image and the retained element

  `DisplayPathComparison`-shaped JSON block (`"display_path"`).

### WP7 — Harness, xtask, CI (`crates/ordo/examples/presenter-lab.rs`, `xtask/src/measure_presenter.rs`, CI)

- `presenter-lab` modes: interactive (owner review), `--measure <json>`,
  `--baseline <mode> <json>`, `--display-path <json>`; each measuring mode
  quits itself when done.
- `cargo xtask measure-presenter` runs the engine bench (unchanged), then the
  lab in release: measure once, display-path once, each baseline three times;
  merges into `report.json`; fails if keydown→paint p95 ≥ 50 ms, any RSS

### Review round (F2)

- One `GoTo` action: a jump to any Cue is a single command with one navigation
  sample, not a run of arrow keys.
- Paint stamps are per surface, taken in each surface's canvas paint. The
  `keydown_to_surface_paint` scope stops before GPU present.
- The present figure is an upper bound: keydown to the settle callback, at
  most one frame late. It is reported separately as
  `keydown_to_present_upper_bound`.
- The measure run opens the real operator runtime first, so the production
  hot-path notes (preference saves, canonical sends, storage file access) are
  reachable. The oracle compares the full final state, revision included.
- Peak RSS is sampled every 250 ms on a background task (`peak` in the
  report). Peak private bytes stay `null`: sysinfo 0.31.4 cannot read
  `PrivateUsage` on Windows, and reading it directly needs unsafe FFI.
- Startup is measured to the frame after the first present
  (`startup_scope: process_start_to_next_frame_after_first_present`).
- Baseline modes carry honest names: `empty_shell`, `preparation_stand_in`
  (no Preparation UI or storage exists yet), and `presenter_probe_in_runtime`
  (500 canonical frames through the bounded `FrameCache` and the visible-only
  `ThumbnailCache`).
- Timeouts scale with the command count: 30 s plus 100 ms per command.
- The temporary preferences file is removed on every exit path.

## Recorded results (WP5–WP7, owner's machine)

`cargo xtask measure-presenter` in release on the owner's development machine
(AMD Radeon(TM) Graphics, hardware, `software_emulated: false`), accepted as
minimum-profile hardware for now. CI's `windows-2022` run is recorded
separately in its uploaded `report.json`.

- **Keydown → surface paint** (`keydown_to_surface_paint`, stops when the
  surface's paint runs, before GPU present), 2,000 seeded commands over 500
  Cues, p50 / p95 / p99 ms:
  navigation 1.15 / 1.71 / 1.95 (Preview), 1.20 / 1.74 / 1.99 (Program);
  Freeze 1.10 / 1.72 / 1.92, 1.13 / 1.75 / 1.95;
  Blackout 1.19 / 1.76 / 2.00, 1.23 / 1.80 / 2.02;
  Space 1.12 / 1.60 / 1.93, 1.16 / 1.66 / 1.95.
  Upper bound to the next frame after present: p95 about 14 ms for every
  command (at most one frame late).
- **Frames:** 2,001 presented, 1 dropped. **Worker queue** p95 0.08 ms.
  **Idle CPU** 7–10 % (higher than expected for an idle window; not yet
  explained). **Hot-path violations:** 0. **Oracle:** full final state,
  revision included, matches.
- **Startup:** about 400 ms from process start to the next frame after the
  first present.
- **Memory:** measure-run peak RSS 50.9 MiB. Private bytes are unavailable:
  `sysinfo 0.31.4` does not read `PrivateUsage` on Windows, and reading it
  directly needs `unsafe` FFI, which the workspace forbids. GPU allocations
  are unavailable for the same reason.
- **Display paths** (30 passes, notify → next frame after present, same
  one-frame bias for both): CPU raster 53.1 ms median, 16.8 MB held (RGBA,
  PNG, and GPUI's decoded image; GPU texture excluded); retained scene
  13.3 ms median, 0.24 MB held (glyph-mask upper bound). The retained path is
  about 4× faster and holds about 70× less per slide, which is the input
  T1.3's scope waits on.
- **Baselines, RSS MiB, three fresh processes:** empty shell 47.1 / 47.2 /
  47.4; Preparation stand-in (synthetic 10,000-entry library, no Preparation
  UI or storage yet) 52.5 / 52.6 / 52.7; Presenter probe in the runtime with
  500 Cues through the bounded frame and thumbnail caches 179.6 / 179.7 /
  179.6 (peak about 300 during frame generation). All within the 512 MiB
  budget and the 1 GiB ceiling.

AC still open after this round, and why:

- **Hot path clean:** the probe runs inside the real runtime and reports zero
  notes at image decode, file access, canonical recomposition, and preference
  save. SQLite, pagination, and autosave do not exist yet, and a blocking
  worker wait and a full-timeline rerender are not instrumented.
- **Record RSS/private memory…:** met. Private memory and exact OS peaks come
  from `platform::process_memory` (Decision 269); one lab run reported 138 MiB
  private, 155 MiB peak private. GPU allocations are recorded as unavailable
  because the pinned GPUI does not expose its device.
- **Three-run baselines:** the numbers are in budget, but "large-library
  Preparation" is a stand-in until a Preparation workspace exists.
