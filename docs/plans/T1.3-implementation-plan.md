the minimum-profile church PC (`docs/plans/T0.6-implementation-plan.md`,
Recorded results): the retained scene is about 4× faster (13.3 vs 53.1 ms
median; 17.2 vs 66.8 ms on the church PC) and holds about 70× less per slide
(0.24 MB vs 16.8 MB). No decision record adopted either path. This plan
records **Decision 310 (accepted by the owner on 2026-11-04, `docs/decisions/0310-live-output-draws-the-retained-frame-rasterize-only-for.md`): live output and monitors draw the logical
`Frame` through the retained path; rasterization stays for thumbnails only
where needed, transitions, capture, and export.** Under it, per the T1.3 task
text:

- Dropped (annotated in `MILESTONES.md`, left unticked for the owner): the
  full-resolution raster scheduling/eviction criteria (AC 1 byte-budget
  half, AC 2 separate low-resolution thumbnail raster cache, AC 3 decoded
  raster eviction).
- Kept: Program/Preview frames pinned while in use and a fixed preload bound
  (now over logical `Frame` values, counted, not byte-budgeted); obsolete
  requests cancelled or ignored (AC 4); decode/render failure → one
  structured Unavailable result consumed by the Engine and Preflight (AC 5);
  the 500-Cue memory envelope (AC 6) and the E2E.

## Shaping constraints

- **`rendering` stays at its qualified dependency set** (`RENDERING-T0.4.md`):
  the store and scheduler are std-only state machines; no threads inside.
  Work runs on the caller's executor (platform task worker / test harness),
  so tests drive slow and failed jobs deterministically.
- **Latest wins per slot, wanted-ness per key.** Program and Preview each
  want one key and a new request supersedes the slot's previous one; the
  preload set is replaced wholesale. A key is wanted while Program, Preview
  or the preload set names it (key membership, not generation), and there is
  one job in flight per key. Generations only identify tickets. A completed
  frame whose key is no longer wanted is ignored and dropped; a failure is
  stored as Unavailable regardless. `FrameScheduler::obsolete()` lists
  in-flight tickets the executor may abandon (`abandon` refuses a ticket that
  became wanted again); run both after each request pass to bound in-flight
  jobs at `2 + 2 * PRELOAD_RADIUS`.
- **No partial frame.** The cache only ever holds a complete composed `Frame`
  (`Arc<rendering::Frame>`) or a structured `Unavailable`.
- **T1.4 consumer rule.** While Program's key is still in flight the Program
  monitor keeps the last frame it drew (it is complete) and the output window
  likewise; black reaches them only through Engine state.
- **Unavailable is one type.** `rendering::UnavailableReason` (`Render(RenderError)`,
  `DecodeFailed`, reserved for the T1.4 image decoder; a missing image is
  `Render(MissingForegroundImage)`), keyed by the caller's frame identity. The
  Engine gains a runtime availability overlay entering through
  `Command::FrameUnavailable { frame, reason }` (wrapper
  `Engine::mark_frame_unavailable(frame, reason, now)`); every Cue projecting
  that frame becomes non-presentable (Decision 274 rules apply) and
  `Engine::cue_availability(flat)` (`None` out of range; `preview_availability()`
  for Preview) is the single structured result. Nothing from a failed render
  reaches Program: Program's frame is set before composition runs, so a failure
  for it means it was never drawn. Linked Live goes black with
  `unavailable_black`, Frozen goes black, and a running auto-play on the failed
  Cue advances to the next advancing Cue (or stops). A frame no Cue uses is
  ignored.
- **Pinned.** The Program and Preview frames are never evicted; the caller
  chooses preload keys (at most `2 * PRELOAD_RADIUS`, normally the Cues either
  side of Preview); the cache capacity is clamped to at least
  `2 + 2 * PRELOAD_RADIUS`; everything else is
  evictable by count (`FRAME_CAPACITY`).
