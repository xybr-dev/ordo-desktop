## Outcome

The parish library accepts content from outside Ordo in two ways, and neither ever opens a PowerPoint file:

- **Machine exchange (`.ordo`).** **Import .ordo** on the Songs screen picks one or many `song-import` `.ordo` files. Each is inspected (container limits, manifest, payload hash) and its JSON payload validated against the published **song-import v2** contract before anything changes. A full-workspace **Review Song import** view rises over Library → Songs: a document list on the left (title, file name, a classification chip), the selected document on the right (Imported document and Song in the Library cards, Song-identity evidence, one block per contained Arrangement with its evidence and staged action), and a footer **One Library update** / "If any approved change fails, none of them is saved." with a summary and **Import approved**.
- Every valid document resolves its Song identity once (an existing Song by stable identity or by an unambiguous normalized title/alias match, a new Song, or **Needs decision**). Every contained Arrangement is then classified on its own as **Add new Song**, **Attach Arrangement**, **Skip unchanged** or **Needs decision**, each with concrete evidence (identity, names, attribution, opening line, lyrics, Sequence, slide boundaries).
- A changed near-duplicate Arrangement is **Needs decision** with **Add as new Arrangement**, **Update existing Arrangement** or **Skip document**. Update states its reach inline (the Choirs that use it; Mass-local copies don't change) and, on commit, replaces the whole Arrangement as one restorable `replacement` revision under its existing identity.
- **Compare contents** opens one read-only, wide slideover with **Overview**, **Lyrics**, **Sequence** and **Slides**, the imported Arrangement beside its nearest local candidate (selectable when there are several), and returns with **Back to review** without changing the staged action.
- An invalid document (bad container, failed contract, unsupported newer version, any invalid contained Arrangement or reference) stays listed as **Invalid** with the exact reason, **View technical details**, **Remove from review** and **Choose another file**, and never contributes a mutation.
- **Import approved** is disabled while any **Needs decision** row is open. Committing writes every approved mutation in one storage transaction; any failure leaves the whole batch unchanged. Reimporting the same unchanged documents classifies everything **Skip unchanged** and writes nothing.
- **Human authoring (`.md` / `.txt`).** Picking one Markdown or text file opens an unsaved **Markdown song** draft: YAML front matter for Song and Arrangement details, the body in an editable source area, a live preview of the parsed sections, Sequence and slide boundaries, inline issues (unresolved or ambiguous `[Repeat: …]`, missing title, unlisted language), and the ordinary possible-existing-Song count and identity preview from New song. **Save** creates the Song and its Arrangement (or attaches the Arrangement to a chosen existing Song) in one transaction; unresolved repeats save as an unready draft.

## Shaping constraints

- **Domain stays dependency-free.** JSON, ZIP and files never enter `domain`. The domain owns the typed import document, whole-document validation, the Markdown parser (plain text in, typed draft out), identity resolution, classification, evidence and the plan; `storage::exchange` turns bytes into that typed document.
- **Nothing mutates before commit** (Decisions 135, 223). Staging reads files and the in-memory library only: no revision backfill, no Choir creation, no temporary rows. The one write is the commit transaction.
- **One transaction, re-checked.** The commit re-checks every identity it inserts, every parent it replaces, every Song it attaches to and every Choir it links inside the immediate transaction; any failure (including an injected one at any statement) leaves the whole batch and the library unchanged.
- **Whole documents, whole Arrangements.** A document with any invalid part is excluded whole (Decision 137); an Update replaces the whole Arrangement as one revision and never merges sections, lines, Sequence or pagination (Decision 136).
- **Classification is evidence, the operator decides.** No title or alias match ever overwrites; every suggested action can be changed; Needs decision blocks commit until chosen (Decisions 39, 135, 136).
- **No work on the GPUI thread.** File reads, inspection, decoding, Markdown parsing of a picked file, classification of a batch and Slides composition run in `cx.background_spawn` or the store's worker; the Markdown draft re-parses on edit off-thread with a generation counter.
- **Copy.** Verbatim from the approved mockup above; where none exists, from MVP-PLAN 6.24's wording or listed for approval (Decision 24). No task ids in visible copy. Refusals are mapped to operator copy, never shown raw (T2.7a rule); the raw finding lives behind **View technical details**.
- **Editor ground rules.** Real parish store rig, real keys and clicks, exact strings and ids; F6 order actions, primary list, main pane; slideovers trap focus and return it to their invoker; list rows `Role::ListItem` with names and current state; the radio group exposes `Radio` roles with checked state; icon buttons named with tooltips; the UI never constructs `PaginationState::Approved`.
- **Changes paths.** `crates/domain/src/song_library/import/`, `crates/ordo/src/songs/import_review/`, `contracts/song-import/` and `tests/fixtures/song-import/` are new as written. `tests/e2e/songs/import.*` does not exist: the E2E lives in `crates/ordo/src/songs/e2e.rs` like T2.4-T2.9's. Files outside the line (`crates/storage/src/exchange/`, `parish_store/import.rs`, `revisions/write.rs`, the store, `history/compare.rs`, ui primitives and assets, `shell.rs`, `songs/library/list.rs`, `contracts/container/`, `docs/contracts/README.md`, test files) are added by WP14's amendment.

## Decisions made while planning (owner to confirm)

1. **Publish song-import v2; v1 stays frozen and is refused.** v2 matches the domain and Decisions 16/40 instead of the spike's slide list:
   ```json
   {
     "schema_version": 2,
     "id": "<UUIDv4, the Song work>",
     "title": "…", "aliases": ["…"], "composer": "…", "source": "…", "rights": "…",
     "liturgical_moments": ["…"], "occasions": ["…"],
     "arrangements": [{
       "id": "<UUIDv4>", "title": "…", "languages": ["Cebuano"], "choirs": ["Koro San Roque"],
       "translator": "…", "adapter": "…", "occasions": ["…"], "notes": "…",
       "extraction_warnings": ["…"],
       "content_sha256": "<hex>",
       "sections": [{ "id": "<UUIDv4>", "label": "Koro", "slides": [{ "lines": ["…", "…"] }] }],
       "sequence": ["<section id>", "…"]
     }]
   }
   ```
   Field names follow the Markdown front matter (Decision 260) so both inputs share one vocabulary: `composer` → Song attribution, `source` → provenance, `rights` → rights notes, `translator` / `adapter` → Arrangement rendition attribution (Decision 11 joins them), `notes` → Arrangement notes. `languages` needs at least one entry from Ordo's built-in list (Decision 11). `sections` needs at least one entry and each section at least one slide of at least one line; `label` is optional (absent = unlabeled). `sequence` needs at least one entry and every entry names a section of the same Arrangement (`missing-reference`). `content_sha256` is the SHA-256 of every line in section order then slide order, each followed by LF (the v1 rule with sections), so the T0.8 corpus categories (tampered-hash included) carry over. `extraction_warnings` are shown as evidence and never stored (Decision 40). Optional members are omitted, never `null` (Decision 311's rule). Unknown members, duplicate ids anywhere in one document and duplicate section labels are not contract errors; duplicate **ids** are (`schema`). The container manifest's `schema_version` becomes a per-kind integer (`minimum: 1`; README §5 already describes per-kind refusal), and this build supports `song-import` v2 only: a v1 payload is refused with "requires an Ordo version supporting song-import v1; this build supports v2". A non-empty `assets` list in a song-import container is Invalid ("song-import v2 carries no assets"). *Reason:* v1 cannot carry sections, Song metadata or the Markdown fields, and nothing has shipped in its shape (Decision 311's argument). *Alternatives:* (a) keep v1 and map each slide to a one-slide section (loses the section/slide distinction and every Song field the parish already records); (b) accept both v1 and v2.

2. **The production reader lives in `crates/storage/src/exchange/`, ported from the spike, not in a new crate.** `exchange::container` ports `inspect` (limits, path safety, duplicate and unlisted entries, manifest, payload size and hash) for the `song-import` kind; `exchange::song_import` validates and decodes the v2 payload into the domain's `ImportDocument` with the same JSON-Pointer findings and codes. `storage` gains `zip.workspace = true` (it already has the spike's `serde_json` and `sha2` pins). The spike stays for `tests/artifact-container` (Decision 306). *Reason:* MILESTONES 33-39 make `crates/portability/` conditional until T4.1; MVP-PLAN 6.4 says the Module stays in the closest existing production crate that preserves dependency direction; `storage` already owns "atomic file operations" and depends only on `domain`. *Alternatives:* extract `crates/portability` now (a new edge in `xtask` and a T4.1 decision taken early); put the reader in `crates/ordo` (a view crate holding archive rules).

3. **Stable identity: the document's Song and Arrangement ids become the local ids; section and occurrence ids are minted locally.** Add new Song creates the Song under the document `id`; a new Arrangement takes the imported Arrangement `id`. Section and occurrence ids are random new ones (the store's id source), because the domain reserves them forever per Arrangement and AI-authored files reuse example ids. Skip unchanged therefore compares **structurally** (Decision 5), never by section id, and reimport is idempotent by Song/Arrangement id plus equal content (AC10). When the imported Arrangement id already belongs to a different Arrangement than the one being created (Add as new over a same-id local Arrangement), the new Arrangement gets a fresh id too. *Reason:* Decision 40 requires stable ids for the Song work and Arrangements; the domain's per-Arrangement section reservation makes adopting section ids collision-prone for no user-visible gain. *Alternative:* an `import_identity` mapping table (migration 0008) keeping local ids random (a second identity system before Phase 4's reconciliation anchors exist).

4. **Song identity resolves once per document, in this order** (all comparisons by `match_key`, so case and spacing never matter; near matches by `identity_key`):
   1. The document `id` is a local Song → **that Song** (evidence: "Same Song work." plus whichever names match). Its title need not match; a title that matches nothing adds the evidence "The file names it {title}".
   2. Otherwise, if any contained Arrangement `id` is a local Arrangement, the Songs owning them are candidates; exactly one → **that Song**.
   3. Otherwise `possible_existing_songs` on the document's `SongDraft`: exactly one Song with an `ExactTitle` or `ExactAlias` match → **that Song**, suggested and changeable.
   4. Several exact candidates, or only near candidates, or rule 2 with several Songs → **Needs decision** (Song): choose one candidate or **Add as a new Song**.
   5. No candidate → **Add new Song**.
   An archived resolved Song cannot take an Arrangement (`create_arrangement` refuses it): the document becomes **Needs decision** with only **Add as a new Song** and **Skip document**, and the evidence "{title} is archived. Restore it to attach to it." Supporting evidence (never a candidate on its own): same attribution (`SameAttribution`) and same opening line (first slide line of the first sung section, by `match_key`, Decision 39).

5. **Each contained Arrangement is classified on its own against the resolved Song** (pure `classify_arrangement`):
   - Song is new (rule 5 or the operator's **Add as a new Song**) → **Add new Song** (evidence "Creates the Song work and its first Arrangement." 166, or "…and its {n} Arrangements" for several).
   - Same Arrangement id under that Song: equal content → **Skip unchanged**; different → **Needs decision** with **Update existing Arrangement** recommended (the stable id proves update intent, Decision 136).
   - Otherwise the nearest local Arrangement of that Song (active and archived) by: equal content, then same language set **and** a shared Choir, then same language set **and** same opening line, then same title. Equal content → **Skip unchanged** ("Identical to the existing {label} Arrangement: lyrics, Sequence and slide breaks all match." after 164). A "resembles" match that differs → **Needs decision** with **Add as new Arrangement** recommended (Decision 136). No resembling Arrangement → **Attach Arrangement** (evidence names the reason: no Arrangement for that Choir, or a new language rendition, Decision 88).
   - **Equal content** means: same title, language list, Choir names (case-insensitive set), rendition attribution, occasions (set), notes, the same section labels and lyrics in order (slide breaks included), and the same Sequence as a list of section positions. Pagination **states** are ignored (imported content always begins NeedsReview), so a library Arrangement the operator approved since the last import still counts as unchanged.
   - Differences are reported as structured evidence (`ArrangementDifference::{Details(fields), SectionReworded(label), SlideBreaks(label), SectionAdded(label), SectionRemoved(label), SequenceChanged}`, sections paired by label then position) and composed into the mockup's sentence form ("Resembles the existing Koro San Roque Arrangement: Bersikulo 2 is reworded, a Bersikulo 3 is added, and the Sequence ends differently." 157).
   - Archived local Arrangements can be the nearest match and can be Skip unchanged; **Update existing Arrangement** over an archived one is not offered (it is inspect-only, Decision 148): the row offers **Add as new Arrangement** and **Skip document**, with "The existing Arrangement is archived."

6. **Inside one batch.** Documents are classified in file-name order against the library **plus the new Songs staged by earlier documents**: a later document with the same Song id as an earlier **Add new Song** document attaches to that staged Song (evidence "Same Song work as {file}"), and the earlier document's Song details win (a difference is evidence, not an error). A later document that repeats an Arrangement id another valid document already uses is **Invalid** ("Arrangement {id} is also in {file}.") because one identity cannot be two Arrangements. Removing a document from review reclassifies the rest.

7. **Imported sections begin NeedsReview; Markdown sections begin Draft.** `.ordo` content gets `PaginationState::NeedsReview` per section (Decision 40: preserved breaks are hints, not approved pagination), set by the domain plan, never by the UI. Markdown is authoring, the same as typing the sections in the editor, so it saves Draft. *Alternative:* both Draft (loses Decision 40's distinction in readiness); both NeedsReview.

22. **Markdown rules (pure `import::markdown::parse`).**
    - Input is UTF-8; a BOM and CRLF are accepted; anything else is a blocking issue "This file isn't UTF-8 text.".
    - **Front matter** is required because it carries the required title: it starts on line 1 with `---` and ends at the next `---` (missing: blocking issue "Add front matter with a title."). A strict YAML subset: `key: value`, `key: [a, b]` and block lists (`- item` under `key:`); single- or double-quoted scalars; `#` comments. Keys (Decision 260): required `title`; optional `aliases`, `composer`, `source`, `rights`, `arrangement` (Arrangement title), `language` (one name or a list), `choirs`, `translator`, `adapter`, `liturgical_moments` (Song), `occasions` (Arrangement, the planning filters' level), `notes` (Arrangement). An unknown key is a non-blocking issue "Ordo doesn't use {key}; it's ignored."; malformed front matter is blocking, with its line.
    - **Body.** Lines before any label belong to an unlabeled section. `[Label]` alone on a line starts a new section with that label (trimmed). `[Unlabeled]` starts a new label-free section. A blank line (whitespace only) is a hard slide boundary inside the current section; runs of blank lines are one boundary; leading and trailing blanks in a section make no slide. A label that appears twice starts two sections (the domain allows duplicate names); it makes a `[Repeat:]` of that label ambiguous.
    - `[Repeat: label]` alone on a line adds an occurrence of the section whose trimmed label matches by `match_key`, whether it is defined earlier or later. Text after a `[Repeat:]` line with no new label starts a new unlabeled section.
    - **Sequence** is document order: each section contributes one occurrence where it is defined, and each repeat one occurrence where it appears.
    - Unresolved (no match) or ambiguous (several) repeats are non-blocking issues on their line: "No section is called {label}." / "{n} sections are called {label}. Rename one." The draft stays saveable (Decision 23).
    - Other issues: a section with no lyrics (non-blocking, "{label} has no words yet."), no sections at all (non-blocking; the Arrangement saves empty, as Create Arrangement does), missing or blank `title` (blocking), unlisted language (blocking, Decision 11), a bracket line that is not a label (`[ ]`, unbalanced) kept as lyrics with a non-blocking issue.

23. **An unresolved repeat saves as a placeholder section.** On Save, each unresolved or ambiguous `[Repeat: X]` becomes an occurrence of a new empty section labelled exactly "X" (one per distinct unresolved label). `readiness` reports it `NoLyrics`, so the Arrangement is Incomplete ("saveable but unready", AC2) and the operator repairs it in the ordinary editor (type its words, or remove and repeat the intended section). *Reason:* the domain Sequence cannot hold a dangling reference, and dropping the occurrence would make an incomplete song look ready. *Alternative:* drop unresolved occurrences on save and keep a note in the Arrangement notes.

## Risks / unknowns

- **Contract churn.** Decision 1 changes a published (spike) contract and the container manifest schema. If parish migration agents have already produced v1 files, v2 strands them; ask the owner before WP1 whether any v1 files exist. Alternative (b) (read both) is the fallback.
- **Language matching vs AI output.** v1 fixtures use ISO codes; v2 refuses them (Decision 11). Expect AI-authored files to fail on language until the guide is followed; the Invalid reason names the value. If this bites in practice, add codes to `languages.rs`.
- **Adopted identities collide with sloppy files.** AI tools copy example UUIDs. Decision 3 adopts only Song and Arrangement ids; a copied example Song id resolves to the wrong Song by rule 4.1. The evidence line "The file names it {title}" surfaces it, but the classification is still "that Song"; consider making an id match with no name match a **Needs decision** if review shows confusion.
- **"Resembles" heuristics.** Decision 5's ladder (language + Choir, language + opening line, title) is a guess at what a parish means by "the same rendition". Wrong guesses only change the **recommended** outcome and whether the row is Attach or Needs decision; nothing commits without the operator. Tune with real parish exports before T2.10c freezes.
- **Equal content ignores pagination states.** An Arrangement the operator approved since the last import is "unchanged"; a reimport of the same file never resets approvals. That is intended (Decision 5) but means an Update is never proposed for state-only differences.
- **Commit size.** One transaction for a large migration batch (hundreds of documents) holds the write lock for its duration and builds one large `ImportCommittedRecords`. Measure a 300-document batch in the store test; if it exceeds the interaction budget, show the named progress indicator during commit (the UI already disables the button).
- **Classification cost on the GPUI thread.** It must never run there; `possible_existing_songs` is O(Songs × names) per document. A 300-document batch against a 1,000-Song library should stay well under a second off-thread; measured in the store test.
- **Placeholder sections (Decision 23).** A placeholder section named like a real one adds a duplicate label; the editor already tolerates stored duplicates, but the operator may not see why. The readiness finding names it; Decision 24's copy is a candidate for a clearer "Repeat target missing" wording later.
- **Markdown front matter is a YAML subset.** Anchors, multi-line scalars and nested maps are refused as "BadFrontMatter" with a line; files written by tools that emit full YAML may need simplifying. The guide (§13) shows the accepted forms.
- **File picker on Windows.** `prompt_for_paths` at this revision has no type filter and its behaviour under the vendored Windows patch is untested; the `FilePicker` seam keeps every test independent of it, and the lab exercises the real dialog. A failure to open the dialog maps to "Couldn't open the file picker." (add to Decision 24 if seen).
- **History comparison after Update.** Decision 13's alignment pairs by label; sections renamed by the import pair by position only among unlabeled ones, so a renamed section shows as removed plus added. Acceptable; it matches the comparison's "never merges" stance.
- **Stale review.** The shell keeps other editors closed while the review is up, but a background write (another window is out of scope) could still move a head; Decision 14's stale refusal is the safety net, tested in WP5 and WP6.
- **Copy approval.** Decision 24 lists strings with no mockup; T2.10b's PR body lists every one again, and review may change them. The Markdown draft has no approved reference at all; the owner may want a mockup before WP10 starts.
