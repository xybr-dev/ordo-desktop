## Outcome

There is one edit-safety mechanism, and every authoring screen will reuse it:

- An editor session holds the content of the one Song or Arrangement that is open.
- Text edits coalesce into one committed point after one second of inactivity, or when focus leaves the field.
- Structural changes (add, remove, reorder) and semantic replacement each commit as their own point.
- Each committed point atomically updates the entity and appends a durable Edit revision. The revision records its content hash and links to its parent.
- Undo and Redo walk an in-memory stack that belongs to the open entity. The stack is cleared on navigation or restart.
- Undo, Redo and restoration all commit a new, later revision; history is never rewritten.
- A focused text field keeps Ctrl+Z for its own native text Undo.
- The header shows **Saving…**, **Saved** or **Couldn't save**. An edit that failed to save stays pending and blocks silent navigation (Retry save / Keep editing / Leave without saving).

## Shaping constraints (verified)

- **No editor UI exists yet.** The Song and Arrangement editors arrive in T2.4 through T2.8. T2.2 therefore delivers a generic `EditSession`, plus a test harness view and a lab that drive it with real `ui::Field`s. The real editors adopt it later.
- **The app does not open the parish database yet** (`crates/ordo/src` has no `storage::` use). `EditSession` talks to persistence through a small async port trait. In-app wiring happens when the editors land; the lab and the E2E use a real `Storage`.
- **Field Undo is base-owned.** `ui::Field` wraps `gpui_base::input::InputState`, which owns text editing and native Undo/Redo. GPUI dispatches a key to the focused element first. So with the session's Undo action bound on the editor container, a focused Field consumes Ctrl+Z; when no text field has focus, the container handles it. This is verified in WP3 against the pinned `gpui-base` source before it is relied on.
- **Revisions need content.** The T2.1 `edit_revision` placeholder has only a hash and a parent. Migration 4 replaces the still-empty placeholder with the real table. No product code has written it yet.
- **Serialization.** `serde`/`serde_json` are already pinned in the workspace (used by `presentation`). The payload is canonical JSON of the content, and the hash is SHA-256 of those bytes.
- **Time.** The domain mechanics take explicit `Timestamp`/millisecond inputs and are pure. The GPUI layer owns the timers (`cx.background_executor().timer`).

## Work packages

### WP1: Domain revision mechanics (T2.2a). Design-sensitive: new invariants.

`crates/domain/src/revisions.rs`, pure and generic over the content type `C: Clone + Eq`:
- `RevisionEntity { Song(SongId), Arrangement(ArrangementId) }`.
- `RevisionKind { Creation, Edit, Import, Replacement, Restoration }`. Only `Edit` groups into sessions; every other kind stands alone (Decision 140/141).
- `TextCoalescer`: `edited(now) -> EditGeneration`, `is_due(now) -> bool` with a 1000 ms inactivity window, `focus_left() -> bool`, `generation()`, `due_in(now)`, and `settle(generation)`, which clears the pending edit only if no newer edit was recorded since that generation (typing during an in-flight save stays pending). Callers feed it monotonic time.
- `UndoStack<C>`: `commit(C)`, `peek_undo()`/`peek_redo()`, `undo()`/`redo()`, `can_undo()`/`can_redo()`. A new commit clears redo and an equal state is ignored. The caller peeks, commits the durable revision, and calls `undo()`/`redo()` only after that commit succeeded, so a failed save leaves the stack unchanged. `clear()` handles departure.
- `HistorySession` assignment: `SessionClock::on_edit(entity, now, fresh) -> HistorySessionId` (the caller supplies the fresh id) and `end()`. A new session starts on the first commit after open, after navigation to another entity, after close, or after more than 30 min without a commit.
- `group_history(&[RevisionSummary]) -> Vec<HistoryEntry>`: consecutive `Edit` revisions with the same session id form one entry; standalone kinds are separate entries.
- Tests cover every boundary: exactly 1000 ms, 999 ms, focus departure, no-op edits, the 30-minute edge, Song vs Arrangement never merging, and standalone splits.

### WP2: Revision storage (T2.2b). Design-sensitive: atomic dual write.

- `migrations/0004_edit_revisions.sql` drops the empty `edit_revision` placeholder and creates the real one:
  - id, song_id/arrangement_id (exactly one), parent_id
  - kind, session_id (canonical v4, NULL for standalone kinds)
  - content (TEXT, canonical JSON), content_sha256, created_at
  - `UNIQUE (parent_id)`, which keeps one linear chain per entity
  - indexes
- Re-bless `ERD.md`.
- `crates/storage/src/revisions/`:
  - `SongContent` and `ArrangementContent`: the editable content (Song details; Arrangement title, languages, Choir links, occasions, sections with ids, Sequence with ids).
  - `commit_song_revision` and `commit_arrangement_revision`, each taking `(entity, content, kind, session)`. In one IMMEDIATE transaction they replace the current rows with `content` (keeping section and occurrence ids from the content) and append a revision whose parent is the entity's latest revision. Both return the `RevisionRecord`.
  - `create_song` and `create_arrangement` now also append a `Creation` revision in the same transaction.
  - `revisions_for(entity)` and `revision(id)` read history.
  - `restore_revision(id, session)` commits that revision's content as a new `Restoration` revision.
- Commits carry `expected_parent` and refuse stale bases (`StaleRevision`); there is one `Creation` root per entity.
- Tests cover: hash equals SHA-256 of the payload; the parent chain is linear; restoration appends a revision; an injected failure leaves both the content and the history unchanged; the content round-trips.

### WP3: GPUI edit session (T2.2c). GPUI-facing, Sonnet.

`crates/ordo/src/edit_session/`:
- `EditSession<C>` entity: the current content, `TextCoalescer`, `UndoStack`, `SessionClock`, a `SaveState { Saved, Saving, CouldntSave { pending } }`, and the `RevisionPort` trait. Every commit runs off the GPUI thread through the port's future. A failure keeps the pending content and sets `CouldntSave`. `request_navigation()` flushes first and, on failure, returns a guard choice.
- Ctrl+Z / Ctrl+Y actions on the editor container.
- Undo and Redo commit as `Edit` revisions in the current History session, after flushing any pending text edit. While a save is in flight, or a pending edit failed to save, Undo, Redo and restore are blocked until it settles.
- A focused `gpui-base` Input always consumes Ctrl+Z and Ctrl+Y (bound in its "Input" key context, state.rs:292-294, and never propagated). Editor Undo is therefore reachable only when no text field is focused, which is Decision 139's intended precedence.
- Content loads into Fields with `set_value`, which clears the field's native history, never `replace_all`.
- Flush on window close and quit as well as on navigation. Call `SessionClock::end()` on editor open and on leave.
- A harness view with two Fields and a reorderable list.
- `[UI-AUTO]` tests in `crates/ordo/src/edit_session/tests.rs`: native Undo first, the save states, and blocked navigation.
