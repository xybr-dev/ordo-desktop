# T0.4 implementation plan

> Active plan. `MILESTONES.md` owns T0.4's status and acceptance gates; this
> file owns only the order in which the work lands. Freeze it at the gate close
> the way `docs/plans/T0.3-implementation-plan.md` was frozen.

## Outcome

Deliver T0.4 as small, green PRs that build one Canonical Slide Renderer in
`rendering` and then prove that a single completed composition survives every
consumer, operator size, operating system, display scale, and output density
unchanged. Keep the crate graph: `rendering` depends only on `domain` and owns
composition, shaping, fonts, and rasterization; `ui` owns the operator-side
viewport wrapper and knows nothing about how a frame was produced; `ordo`
composes the two. No GPUI type enters `rendering`, and no layout decision
leaves it.

Every PR below ends with `cargo xtask verify`. Renderer PRs add the smallest
check for the behavior introduced by that PR, exercised through the Renderer
Interface rather than its internals. T0.4's milestone checkboxes remain open
until the final acceptance PR proves the complete gate.

Three constraints shape the split, and each is load-bearing:

- **`rendering` cannot use GPUI.** The dependency contract in `xtask` permits
  `rendering -> domain` only, and `gpui-base` is private to `ui`. The canonical
  shaping and raster path is therefore its own stack, which is what makes AC 5's
  "explicit and separate from ordinary GPUI operator text layout" structural
  rather than a convention.
- **`ui` cannot use `rendering`.** `ui` has no permitted internal dependencies
  at all. `crates/ui/src/canonical_frame.rs` is consequently a viewport over
  finished pixels plus their logical size — never a renderer caller. `ordo`
  is the only place the two meet.
- **The fonts are already bundled, in the wrong crate.**
  `crates/ui/assets/fonts/` holds both faces for operator chrome, and
  `resources/runtime-manifest.json` lists them by path with no hashes. AC 3
  wants pinned hash manifests and a renderer that can read the same bytes, so
  ownership moves before anything shapes a glyph.

## Dependency chain

```text
T0.1 + T0.2 + T0.3 baseline
        |
        v
PR 1  qualify the shaping and raster dependencies, with a cross-platform probe
        |
        +----------------------+
        v                      v
PR 2  shared bundled fonts  PR 3  Renderer Interface and composition space
        |                      |
        +----------+-----------+
                   v
PR 4  canonical shaping, wrapping, and serialized logical frame
                   |
                   v
PR 5  the canonical template corpus
                   |
        +----------+-----------+
        v                      v
PR 6  golden fixtures      PR 7  rasterization and target density
                   |                      |
                   +----------+-----------+
                              v
PR 8  packaged cross-platform invariance
                              |
                              v
PR 9  the operator viewport wrapper and its four consumers
                              |
                              v
PR 10 T0.4 acceptance, gallery, and manual gate
```

PRs 2 and 3 can be developed in parallel after PR 1, as can 6 and 7 after PR 5.
The rest are intentionally ordered: nothing can shape without qualified
dependencies and reachable font bytes; templates compose on the shaping path;
fixtures and raster both need real templates to be worth anything; invariance
needs a serialized frame *and* a raster to make claims about; and the operator
wrappers consume only finished frames.

## Micro-PRs

### PR 1 — Qualify the canonical shaping and raster dependencies

**Depends on:** T0.1, T0.2, T0.3.

- Record, in `docs/qualification/RENDERING-T0.4.md`, which crates the canonical
  path adopts for shaping, glyph rasterization, and image composition, with
  license, transitive dependency, determinism, and removal-seam evidence. The
  workspace lockfile already carries `rustybuzz`, `swash`, `cosmic-text`,
  `tiny-skia`, `ttf-parser`, `image`, and `png` transitively through the GPUI
  pin; adopting one as a *direct* `rendering` dependency is still a new
  qualified edge and needs its own row.
- Prefer the smallest stack that can state its own determinism. A shaper plus a
  glyph rasterizer that Ordo drives explicitly is easier to hold invariant than
  a layout engine that owns its own line breaking; if a higher-level crate is
  adopted anyway, the row must say what Ordo gives up control of.
- Extend `xtask`'s dependency policy so `rendering`'s direct dependencies are
  checked against a qualified list, the way `QUALIFIED_UI_DEPENDENCIES` guards
  `ui`. Keep the existing `gpui-base`-stays-private check unchanged and add the
  matching one: no GPUI crate may reach `rendering`.
- **Run the invariance probe here, before the stack is committed to.** Shape one
  mixed-script string with the candidate stack, serialize its glyph ids,
  advances, and positions, and compare the artifact produced by a packaged
  Windows run against a packaged Linux run. AC 6 is the milestone's real risk;
  discovering a platform-dependent shaper in PR 8 would invalidate PR 4. The
  probe is evidence in the qualification document, not shipped code.

**Exit check:** the canonical stack is chosen against recorded evidence, its
determinism across both target platforms is demonstrated rather than assumed,
and `cargo xtask verify` fails if `rendering` grows an unqualified or GPUI
dependency.

### PR 2 — Bundle the canonical fonts with pinned hash manifests

**Depends on:** PR 1. Can run in parallel with PR 3.

- Move the Atkinson Hyperlegible Next and Noto Sans faces out of
  `crates/ui/assets/fonts/` to a location both `ui` and `rendering` can
  `include_bytes!` without a crate dependency, and keep their OFL notices with
  them. `ui` keeps using the operator faces exactly as it does today; the move
  is about reach, not behavior.
- Add a pinned content hash per bundled font to
  `resources/runtime-manifest.json` and verify it in the offline-contract gate,
  which today checks only that each declared path exists. Bump
  `schema_version`; the manifest is a committed declaration, not a cache.
- Expose the faces from `rendering` as the only fonts the canonical path can
  load, with Noto Sans as the missing-glyph fallback. There is no system font
  enumeration in `rendering` and no runtime path that consults one; the check
  for that is a test, not a comment.
- Do not build T6.x's versioned runtime font cache, damaged-cache recovery, or
  the Diagnostics font-validation surface. This PR pins and reads bytes.

**Exit check:** a corrupted or replaced font file fails `cargo xtask verify`,
and a renderer test proves a string of glyphs absent from Atkinson resolves
through the bundled fallback rather than through anything installed.

### PR 3 — Add the Renderer Interface and the canonical composition space

**Depends on:** PR 1. Can run in parallel with PR 2.

- Define the resolved semantic content the renderer accepts, including the
  optional authored Response and Responsorial Psalm header strings. `CONTEXT.md`
  is explicit that the renderer never translates or supplies that text: the
  Interface takes the resolved string or the absence of one, and has no code
  path that could produce `TUBAG:` on its own. Keep these input types in
  `rendering` for now; promoting them to `domain` belongs to the milestone that
  gives them persistence and rules.
- Define the Theme input and the target density input, and return either one
  complete frame plus diagnostics or one structured failure. A partial frame
  must be unrepresentable — the success value owns a complete composition, and
  diagnostics ride beside it rather than standing in for missing content.
- Establish the `1920x1080` logical coordinate system and the minimum `120x80`
  safe-area inset from `ui::tokens::canonical_slide`, with a Theme permitted to
  increase and rejected for reducing it. The renderer reads no viewport metric,
  no Interface scale, and no OS scale; there is no parameter through which one
  could arrive.
- Compose header, body, and footer as renderer-owned zones where an absent
  header or footer returns its space to the body. No freely draggable
  positioning, now or behind a flag.

**Exit check:** the Interface's shape makes a partial frame and a language
lookup impossible to express, and a Theme attempting to reduce the safe area is
rejected as a structured failure rather than clamped silently.

### PR 4 — Ship the canonical shaping path and the serialized logical frame

**Depends on:** PRs 2 and 3.

- Implement deterministic shaping, line breaking, and wrapping over the bundled
  faces, entirely inside `rendering`. Preserve authored line breaks, and treat a
  blank source line as a hard Slide boundary that overrides automatic proposals.
- Emit the pagination inputs the Pagination Module will consume — measured
  geometry, line counts, and the fit result — rather than a boolean. Validate
  against measured canonical geometry, never character counts. Split before
  shrinking, never clip, and emit a readiness warning when content cannot fit at
  the approved minimum.
- Serialize the completed logical frame: glyph positions, wrapping, pagination
  inputs, safe area, and element bounds, in a form stable enough to compare
  byte-for-byte. This artifact is what PR 6's fixtures assert against and what
  PR 8 compares across platforms, so its stability is the deliverable, not a
  convenience.
- The canonical path never asks a preview container to reflow. Nothing in
  `rendering` takes a container size.

**Exit check:** the same content, Theme, and density produce byte-identical
serialized frames across repeated runs in one process and across processes, and
a phrase too long for the approved minimum produces a warning beside a complete
frame rather than a clipped one.

### PR 5 — Ship the canonical template corpus

**Depends on:** PR 4.

- Implement the fixed template relationships `DESIGN.md` adopts: Lyrics,
  Response, Reading identification, Reading passage, Responsorial Psalm, Song
  identification, Celebration title, General Text, and General Image, plus the
  black and label-off variants.
- Keep the congregation-facing omissions that are contract, not oversight: no
  First Reading / Second Reading / Gospel labels reach congregation output, and
  a Theme image is background rather than foreground content.
- Apply the adopted relative hierarchy and carry the provisional numeric type
  levels as provisional. `DESIGN.md` names the `72px` projected-response token
  as the first gallery baseline; PR 10 is where levels freeze, and only after
  the gallery holds.
- Enforce the stated line ceilings: pagination targets two logical lyric phrases
  and no more than four rendered lines, and Song and Celebration titles warn
  past three rendered lines.

**Exit check:** every adopted template composes through the same Interface with
its zones, alignment, and reference placement asserted from measured geometry,
and each ceiling produces its warning at the boundary rather than one line late.

### PR 6 — Add the golden fixture corpus

**Depends on:** PR 5. Can run in parallel with PR 7.

- Cover Cebuano, English, Tagalog, mixed scripts, punctuation, long words, and
  missing-glyph fallback across one-to-four lyric lines, Celebration and Song
  identification, Scripture, Psalm, response, General text and image, black,
  label-off, and overflow-warning Slides.
- Supply each multilingual Response and Psalm fixture with its exact authored
  header, since the renderer cannot supply one. A fixture with an absent header
  and a fixture with an empty string are different cases and both belong here.
- Store fixtures under `tests/fixtures/rendering/` and golden serialized frames
  under `tests/golden-frames/`, per the layout `MVP-PLAN.md` already reserves.
  Give the corpus one regeneration command in `xtask`, and make the review of a
  regenerated golden the point of the gate — a golden that updates itself
  silently proves nothing.

**Exit check:** the corpus fails on any change to logical composition, and the
diff a failure prints identifies the element and coordinate that moved rather
than reporting that two blobs differ.

### PR 7 — Rasterize at target density

**Depends on:** PR 5. Can run in parallel with PR 6.

- Rasterize the completed logical frame to RGBA at a target density, feeding
  `presentation::ProgramFrame`, which already exists as the immutable RGBA seam
  every presentation view consumes.
- Target density changes raster dimensions and sampling sharpness and nothing
  else. The logical frame is computed once and rasterized from; density is not
  an input to composition, and the test that proves it compares serialized
  logical frames across densities rather than trusting the call order.
- Keep the canvas square-cornered. The `4px` radius is operator chrome and
  belongs to PR 9; it never enters the render, saved content, or an export.
- Do not build the frame cache, thumbnail preparation pipeline, or emergency
  export here. Rasterization runs off the GPUI thread by construction, because
  `rendering` has no access to it.

**Exit check:** one fixture rasterized at several densities yields different
pixel dimensions and one identical serialized logical composition.

### PR 8 — Prove packaged cross-platform invariance

**Depends on:** PRs 6 and 7.

- Assert byte-for-byte equality of the serialized canonical logical frame across
  packaged Windows and Linux runs, `100%` through `200%` Ordo Interface scale,
  representative system scale, and every output density. This is the milestone's
  `[NATIVE-AUTO]` criterion and the reason PR 1 probes early.
- Run it where the packaged binary runs. Extend the `tests/native-runtime`
  harness rather than adding a workspace member; T0.3's boundary against
  mirroring the illustrative `tests/ui/*` paths applies here too.
- Qualify raster sharpness separately, per platform, and say so in the
  qualification document. This PR makes no claim about pixels — only about the
  composition they are sampled from.
- Interface scale reaching the canonical frame is exactly the isolation test
  T0.3's PR 3 deferred to this milestone for want of a render path. It lands
  here, against real geometry, where it can fail.

**Exit check:** a platform-, scale-, or density-dependent composition fails CI on
both target operating systems, and the failure names which of the four axes
moved.

### PR 9 — Add the viewport wrapper, its consumers, and the rendering lab

**Depends on:** PR 8.

- Add `crates/ui/src/canonical_frame.rs`: one wrapper that takes finished pixels
  plus their logical size and scales them uniformly, clipped inside the `4px`
  slide-viewport chrome, with keyboard focus outside the wrapper rather than
  inside the rendered content. It takes no `rendering` type, because `ui` may
  not depend on `rendering`.
- Consume it from the timeline thumbnail, Inspector, Preview, and Program
  surfaces, composed in `ordo` where `rendering` and `ui` legitimately meet.
  All four display the same completed fixture frame with identical internal
  pixels.
- Add a development-only `ordo` example at
  `crates/ordo/examples/canonical-slide-lab.rs`, launched with
  `cargo run -p ordo --example canonical-slide-lab`. It composes the PR 6
  fixtures through the real `rendering` path and the same canonical-frame
  wrapper the four consumers use; it is not a second renderer or an alternate
  application workflow. Keep it out of `ui-lab`, whose `ui`-only dependency
  contract cannot reach `rendering`.
- Let the lab select every canonical template fixture, label and background
  variants, representative overflow warnings, both viewport presets, every
  Interface scale, and qualified target densities. Show the renderer's
  diagnostics beside the scaled frame so a reviewer can inspect the actual
  Rust output before application workflows exist.
- Interface scale and OS scale may resize a viewport or reduce a thumbnail grid's
  column count, and may not alter the frame inside it. The congregation view
  stays passive, square, and edge-to-edge, and gains no operator semantics.
- Build no Cue timeline, Inspector navigation, or Preview-to-Program behavior.
  These are four viewports onto one frame; their workflows belong to their own
  milestones.

**Exit check:** the four wrappers render one fixture at both viewport presets and
every Interface scale with identical internal pixels, differing only in outer
scale; the development lab renders the complete fixture matrix through that same
path; and no operator-only node reaches the congregation window.

### PR 10 — Close the T0.4 acceptance gate

**Depends on:** PR 9 and all preceding PRs.

- Add the milestone E2E path: render one mixed-language fixture once, display it
  in four different-size operator viewports plus the congregation renderer,
  capture every surface, normalize only outer scaling, and assert identical
  canonical content and unchanged pagination.
- Capture and qualify `design-references/ordo-canonical-slide-layouts*` from the
  running canonical-slide lab. The fixture-backed Canonical Slide Layout Gallery
  covers every adopted template, label and background variants, and
  representative overflow warnings produced by the real Rust renderer through
  the same scaled `1920x1080` composition. Move it into Approved References only
  after the live output and its captured reference are approved together.
- Freeze the projected numeric type levels only once long Cebuano and English
  cases remain comfortably readable in that gallery, and record what changed from
  the provisional levels PR 5 carried.
- Record the `[MANUAL]` evidence in `docs/qualification/T0.4-MANUAL-GATE.md`:
  Atkinson operator fit and Noto fallback legibility and stability in packaged
  Windows and Linux builds at both qualified resolutions, and the gallery
  approval. Only then mark every T0.4 AC and its E2E complete together.

**Exit check:** every T0.4 acceptance criterion has a named automated or manual
piece of evidence, `cargo xtask verify` is green, and no later feature workspace
is implemented.

## Deliberate boundaries

- Do not build the Pagination Module's proposal and review workflow, the
  Presenter Mode surfaces, the Theme Editor, parish storage, or emergency
  PowerPoint export in T0.4. The renderer emits pagination *inputs*; deciding
  slide divisions belongs to its own Module.
- Do not build the versioned runtime font cache, hash recovery, or the
  Diagnostics font-validation surface; `MVP-PLAN.md` 6.27 owns those.
- Do not add a frame cache, thumbnail virtualization, or image-decode pipeline
  before a measurement asks for one.
- Do not let a GPUI type, a viewport metric, or an Interface scale reach
  `rendering`, and do not let `ui` learn what produced a frame.
- Keep tests beside their owning crate; use `tests/native-runtime` for the
  packaged `[NATIVE-AUTO]` gate rather than adding a workspace member.
