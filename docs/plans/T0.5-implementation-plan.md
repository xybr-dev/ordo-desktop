# T0.5 implementation plan

> Active plan. `MILESTONES.md` owns T0.5's status and acceptance gates; this
> file owns only the order in which the work lands. Freeze it at the gate close
> the way `docs/plans/T0.4-implementation-plan.md` was frozen.

## Outcome

Prove safe two-display orchestration behind one Display Control Interface in
`platform`, without letting GPUI or operating-system window types reach
`presentation` or `domain`. The spike lands as one PR built from three work
packages, each ending in `cargo xtask verify`.

Constraints that shape the split:

- **`platform` has no internal dependencies.** The `xtask` dependency contract
  permits `platform -> {}`. Display identity, topology, recognition evidence,
  assignment, and output lifecycle are therefore `platform`-owned value types;
  `presentation` never sees a `DisplayId`, and `platform` never sees a
  `ProgramFrame`. `ordo` is the only place the two meet.
- **The pinned GPUI snapshot has no display-change event and its test platform
  has exactly one display.** Discovery is a snapshot read (`App::displays`), so
  topology refresh is an explicit `refresh(snapshot)` call on the Interface.
  Two-display UI tests therefore drive the in-memory Adapter, and the GPUI
  Adapter is only a translation from `PlatformDisplay` to the Interface's
  value types.
- **Window passivity comes from the Windows backend, not from Ordo code.**
  `WindowKind::PopUp` maps to `WS_EX_TOOLWINDOW | WS_EX_TOPMOST` with no caption
  style, and `focus: false` maps to `SW_SHOWNOACTIVATE` in `gpui-pre-windows`
  `0.3.8`. Ordo asserts the options it requests and mounts no focus handle,
  action, or operator element in the congregation view.
- **The snapshot has no hidden `CursorStyle`.** `unsafe_code` is forbidden, so
  Win32 `ShowCursor` is unavailable, and `hide_cursor_until_mouse_moves` is
  reachable only through GPUI's crate-private platform handle. T0.5 therefore
  ships no pointer hiding; the operator-only cursor locator is a labeled
  direction strip rather than Decision 56's display-layout diagram. Both stay
  under the `[MANUAL]` criterion for the owner to judge.
- **A click activates the congregation window.** `gpui-pre-windows` answers
  `WM_MOUSEACTIVATE` with `MA_ACTIVATE` and `PopUp` lacks `WS_EX_NOACTIVATE`,
  so `focus: false` only governs creation. Ordo re-activates the operator
  window whenever the congregation surface is clicked.
- **An unknown `display_id` falls back to the primary monitor.** Enabling
  output refreshes topology first and verifies the opened window's display,
  failing closed rather than projecting onto the operator screen.

## Work packages

```text
WP1 platform Display Control Interface ─┐
WP2 presentation output lifecycle ──────┼─> WP3 ordo composition, tests/display, CI
```

WP1 and WP2 touch disjoint crates and run in parallel. WP3 composes them.

### WP1 — Display Control Interface (`crates/platform/src/display/`, `congregation_window.rs`)

- Value types: `DisplayId` (opaque OS id), `DisplayEvidence` (name when known,
  persistent uuid when the OS gives one, logical bounds, resolution, aspect),
  `DetectedDisplay`, `Topology` (all displays plus which one is the operator
  display), `RelativeDirection` (eight compass directions plus `Overlapping`)
  derived purely from bounds, never assuming rightward.
- `DisplayAdapter` trait (discovery snapshot) with `InMemoryDisplayAdapter`
  for deterministic tests and `GpuiDisplayAdapter` reading `App::displays()`.
- `DisplayControl` state machine owning assignment (`NotAssigned` |
  `Assigned(evidence)`), output lifecycle (`Disabled` | `Enabled { display }` |
  `Disconnected { evidence }`), recognition (match saved evidence against a new
  snapshot, tolerating a changed OS id; ambiguity never auto-selects), and
  `refresh(topology)` returning typed `DisplayEvent`s. Disappearance of the
  enabled display enters `Disconnected` and never retargets. Reappearance is
  reported as recognized but leaves output `Disconnected` until an explicit
  `enable_output`.
- `congregation_window::options(display)` returns passive `WindowOptions`:
  `PopUp`, `focus: false`, not movable/resizable/minimizable, no titlebar,
  bounds equal to the assigned display, `display_id` set.

### WP2 — Presentation output lifecycle (`crates/presentation/`)

- Enabling output publishes a black Program frame before any content;
  disconnection marks `Disconnected` and drops external Program to black;
  re-enabling after reconnect stays black until an explicit restore command
  takes the current Preview live. Pure, no new dependencies.

### WP3 — Composition, tests, and evidence

- `ordo` startup opens no congregation window (`with_congregation` goes away);
  an explicit enable command asks `DisplayControl` for placement, opens exactly
  one passive window through `congregation_window::options`, and shows black.
  Disconnect closes the window without reopening it elsewhere. Pointer over
  the congregation window raises an operator-only locator whose direction comes
  from `Topology`, never a hard-coded side.
- `tests/display/` (workspace member `display-tests`) drives the milestone E2E
  with the in-memory two-display Adapter and topology fixtures from
  `tests/fixtures/display-topologies/` (left, right, above, below, diagonal).
- A `[NATIVE-AUTO]` test enumerates the real Windows runner display through
  `gpui_platform::current_platform` and the GPUI Adapter, then survives a
  synthetic refresh (display removed, re-added under a new id). CI gains a
  mandatory `windows-display-control` job running it.
