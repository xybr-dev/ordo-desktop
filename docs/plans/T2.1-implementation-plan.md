## Outcome

The T0.7 Storage spike becomes the durable parish foundation. One SQLite
database holds a Parish and its Choirs, Songs, Arrangements, sections and
Sequence occurrences, with placeholder tables for settings, Themes, the
revision ledger, snapshots, packages and backups. Every record has a canonical
lowercase UUIDv4 identity and an explicit creation time; no title is ever an
identity. Image originals live in a managed asset directory under stable IDs
and SHA-256 hashes, and the Storage worker commits an asset and the record that
references it together, so no committed record can reference a missing asset.
Disposable caches live in a separate directory that can be deleted at any time.
`ERD.md` is generated from the migrated schema, and a test fails when it drifts.

Sources:
- `MILESTONES.md` T2.1 (goal, AC, E2E).
- `MVP-PLAN.md` 9.1 (local data, `ERD.md` rule).
- Decision 30: one SQLite owner, managed assets by stable ID and checksum,
  caches are not durable records, no ORM, domain-shaped operations.
- Decision 38: UUIDv4 in canonical lowercase text, explicit creation times,
  uniqueness enforced in storage, regenerate on collision.
- Decision 8 and `CONTEXT.md` Songs: Song work, Arrangement, section,
  Section occurrence, Choir membership.
- Decision 260: `ERD.md` arrives with the authoritative migrations.

## Shaping constraints (verified)

- **Identity already exists.** `domain::presentation::EntityId` parses and
  prints canonical lowercase UUIDv4, and `typed_entity_ids!` makes typed
  handles. T2.1 moves both into `crates/domain/src/identity.rs` and
  re-exports them from `presentation`, so `presentation` and its tests keep
  their paths.
- **Domain has no dependencies** (`domain` has an empty `[dependencies]`), and
  the xtask contract allows it external crates but not OS types. Random bytes
  come from the caller: `EntityId::from_random_bytes([u8; 16])` sets the
  version and variant bits. Storage draws the bytes from `uuid` v4 (already a
  workspace dependency, through `getrandom`), behind an injectable source so a
  test can force a collision.
- **Time.** No date crate in the workspace. `domain::identity::Timestamp` is
  UTC milliseconds since the Unix epoch, with one canonical text form
  `YYYY-MM-DDTHH:MM:SS.sssZ` (civil-from-days arithmetic, no dependency).
  Storage writes it as TEXT with a `GLOB` CHECK so SQL inspection stays
  readable (Decision 38). The clock is injectable for tests.
- **Migrations are append-only.** `0001_parish_profile` and `0002_parish_note`
  are applied checksummed history; editing them would make every existing
  database fail with `ChecksumMismatch`. T2.1 appends `0003_parish_foundation`
  and leaves the spike tables and the spike API alone (T0.7 evidence). `ERD.md`
  marks them as spike tables.
- **The runner owns the transaction.** Migration SQL must not contain
  `BEGIN`/`COMMIT`, and `foreign_keys=ON` is set before migrations run.
- **One owner thread.** All new operations are `worker::submit` closures on
  `Core`, so callers never see SQL, a connection or a transaction (T0.7
  compile-fail doctests keep proving it).
- **Error taxonomy.** `StorageError` gains domain-relevant variants
  (`NotFound`, `MissingReference`, `AssetWrite`, `AssetIntegrity`,
  `InvalidInput`) instead of a second error type, so the existing
  `WorkerUnavailable`/`Busy` paths stay shared. Driver text never decides a
  variant except through SQLite error codes.
- **ERD generation without new tooling.** xtask may not depend on `storage`.
  The generator is a `#[cfg(test)]` module inside `storage` that migrates an
  in-memory database and renders `ERD.md` from `sqlite_master`,
  `pragma_table_info`, `pragma_index_list` and `pragma_foreign_key_list`.
  Ownership and lifecycle notes sit in a Rust table beside it; the test fails
  when a table has no notes, or when `ERD.md` differs from the render.
  `ORDO_BLESS_ERD=1` rewrites the file.

## Schema shape (`0003_parish_foundation`)

All ids are `TEXT PRIMARY KEY` with a CHECK for 36 lowercase characters and
version nibble `4`. All times are canonical TEXT. All foreign keys are declared;
none cascades on delete (Decision 43: archive is non-cascading, deletion is
reference-checked).

- `parish` (single row), `parish_setting` (key/value placeholder).
- `choir`.
- `song`, `song_alias`, `song_liturgical_moment`, `song_occasion`.
- `arrangement` (belongs to one `song`), `arrangement_language`,
  `arrangement_choir` (many-to-many), `arrangement_occasion`.
- `arrangement_section` (belongs to one arrangement; `UNIQUE(id, arrangement_id)`).
- `section_occurrence`: composite FK `(section_id, arrangement_id)` so an
  occurrence can only place a section of its own Arrangement;
  `UNIQUE(arrangement_id, position)`.
- `managed_asset` (`sha256`, `byte_len`, `media_type`).
- `theme` placeholder with an optional `background_asset_id` FK, which is the
  first asset reference and the E2E's image owner.
- `edit_revision` placeholder (entity kind/id, parent FK to itself, content
  hash), owned by T2.2.
- `presentation_snapshot`, `celebration_package`, `parish_backup` placeholders.
- `schema_metadata` (format name; the version is `user_version` and the migration ledger).

T2.3 adds columns it needs through its own migration; T2.1 does not guess
behavior beyond what the E2E exercises.

## Work packages

### WP1: Identity and time in `domain` (T2.1a)

AC: canonical UUIDv4 identities and explicit creation times.

- Move `EntityId`, `IdError`, `hex_digit` and `typed_entity_ids!` from
  `crates/domain/src/presentation.rs` to `crates/domain/src/identity.rs`;
  `presentation` re-exports `EntityId`/`IdError` and uses the macro.
- Add `EntityId::from_random_bytes`, `EntityId::as_bytes`.
- Add typed ids `ParishId`, `ChoirId`, `SongId`, `ArrangementId`, `SectionId`,
  `OccurrenceId`, `ThemeId`, `ManagedAssetId`, each with `from_entity`.
- Add `Timestamp` (millis, canonical text parse/print, round-trip and
  leap-year tests, rejects non-canonical text).
- Files: `crates/domain/src/{identity.rs,presentation.rs,lib.rs}`.
- Tag: **design-sensitive**, because it moves a public type that the snapshot
  reader and the journal depend on, and adds a time codec.

### WP2: Parish foundation migration (T2.1a)

AC: initial migrations cover the listed tables; enforced foreign keys.

- `migrations/0003_parish_foundation.sql`, registered in
  `crates/storage/src/migrations/mod.rs` (the code expects `src/migrations/`
  as the runner and the root `migrations/` directory as the SQL).
- Migration tests: every listed table exists; `PRAGMA foreign_key_check` is
  clean; an occurrence that names another Arrangement's section is refused;
  a non-canonical id or time is refused by CHECK.
- Update the version-pinned assertions (`version == 2`) in storage tests.
- Tag: **design-sensitive**, because the schema is a contract.

### WP3: Generated `ERD.md` (T2.1a)

AC: `ERD.md` corresponds directly to the schema.

- `crates/storage/src/erd.rs` (`#[cfg(test)]`): render the Mermaid overview
  (one entity per table, one relationship per FK) and per-table sections
  (columns, types, null, default, PK, CHECK summary, indexes, FKs, ownership,
  lifecycle). The test compares the result with the committed `ERD.md`.
- `ERD.md` at the repo root, generated.
- Tag: **design-sensitive**, because the render must stay deterministic.

### WP4: Parish store Module Interface (T2.1b)

AC: identities, parameterized writes in transactions, failures preserve state.

- `crates/storage/src/parish_store/`: `records.rs` (plain input/output data:
  `NewParish`, `NewChoir`, `NewSong`, `NewArrangement` with sections and the
  Sequence; `ParishRecord`, `SongRecord`, ...), `write.rs`, `read.rs`.
- `Storage` methods: `create_parish`, `parish`, `create_choir`, `choirs`,
  `create_song`, `song`, `create_arrangement` (sections + occurrences + Choir
  links in one transaction), `arrangement`, `arrangements_for_song`.
- Ids and times are generated by the worker (`IdSource`, `Clock` in
  `StorageConfig`, defaults OS random and system clock). A primary-key
  collision regenerates the id (bounded retries).
- Map SQLite constraint codes to `MissingReference`/`InvalidInput`; check
  referenced rows inside the transaction to name the missing kind and id.
- Tests: SQL-injection-shaped titles round-trip; a failing write (missing
  Choir id, duplicate occurrence position) leaves the prior state
  byte-identical; forced id collision regenerates; a source scan proves no
  `format!` builds SQL in `parish_store`.
- Tag: **design-sensitive**, because of transaction boundaries and error mapping.

### WP5: Managed assets and cache (T2.1c)

AC: stable asset IDs and hashes committed with references; cache separation.

- `crates/storage/src/assets/`: layout `<root>/assets/<id>` (authoritative),
  `<root>/assets/.staging/` (in-flight), `<root>/cache/` (disposable).
- `create_theme_with_background(name, AssetUpload { bytes, media_type })`:
  hash, write staging file, fsync, rename into place, then one immediate
  transaction inserts `managed_asset` and `theme`. Any failure removes the
  file it wrote and leaves no row.
- Open-time sweep: delete staging leftovers and asset files with no row (a
  crash between rename and commit); report a row whose file is missing or
  whose bytes do not match as `AssetIntegrity` from `verify_assets`.
- `read_asset(id)` re-hashes before returning bytes.
- Fault hook (`fault-injection`): fail the next asset write.
- Tag: **design-sensitive**, because of crash ordering and atomicity.

- `crates/ordo/examples/parish-store-lab.rs`: creates a temporary Parish,
  prints the rehydrated records and asset verification, so the owner can see
