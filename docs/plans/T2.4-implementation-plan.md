# T2.4 implementation plan

## Outcome

With T2.4 the running app opens the parish database for the first time. The Library destination's **Songs** and **Choirs** views become real, persistent workspaces:

- **Songs** is the permanent master-detail workspace. Search and filters sit on the left; the selected Song's identity and Arrangements fill the right. It covers the empty, populated, no-match, archived-only and selected states.
- **Search** is normalized and case-insensitive across titles, aliases, attribution/source, Arrangement title/attribution, Choir, language and full lyrics. It ranks title and alias hits ahead of other matches and explains every non-title hit.
- **Filters** (Choir, language, occasion) retain a Song only when one of its Arrangements satisfies every active filter. Missing metadata counts as Unspecified, and the detail pane shows how many Arrangements match out of the total.
- **Include archived** is off by default and never changes archive state.
- **Choirs** is a list-detail workspace:
  - name-only creation, and editable optional details (short label, preferred languages, private notes);
  - rename, plus archive and restore with Show archived;
  - the repertoire table;
  - a duplicate-safe inline quick-create that later selectors reuse.
- **Opening an Arrangement** hands off to a focused Arrangement view. Returning restores the same query, filters, selection and scroll.
- **The other views:** Responses & Prayers and General Presentations keep their existing empty views, with no placeholder repositories or APIs.

## Shaping constraints (verified)

- **The SQLite gate moves.** `xtask` keeps `ordo` storage-free (`validate_presenter_runtime_without_sqlite`). Its own doc says Phase 2 relaxes this for `ordo` "when the runtime first opens the Library database", which is this task. WP3 removes `ordo` from `PRESENTER_RUNTIME`. `presentation`, `rendering`, `domain`, `platform` and `ui` must still never reach `storage`. Presenter Mode never opens the parish store.
- **Data location.** `platform::preferences` already resolves `%APPDATA%\ordo\`. WP3 adds `parish_data_dir()` beside it. `storage::StorageConfig::in_directory(root)` already lays out the database, `assets/` and `cache/`.
- **One owner for the store.** A `LibraryStore` GPUI entity in `crates/ordo/src/songs/` owns the `Storage` handle and the hydrated `domain::song_library::SongLibrary`. It loads off the GPUI thread at startup (a background read, then hydrate). Every write goes through `Storage`, and on success it is applied to the in-memory library. Shutdown follows the existing app-quit path, as T2.2's flush hooks do.
- **Screens live outside the shell.** `shell.rs` owns chrome only (its module doc). The Songs and Choirs screens live in `crates/ordo/src/songs/library/` and `crates/ordo/src/songs/choirs/`. The shell hosts them in its list and viewer regions for the Library destination, replacing `fixtures::rows` for those views only.
- **Search is pure domain** (`crates/domain/src/song_library/search.rs`) over the hydrated library. A Parish holds hundreds of Songs, so a full in-memory scan per keystroke is well within budget, but WP2 measures it with a 2,000-Song fixture to be sure.
- **Choir preferred languages** use the same language values as Arrangements (free BCP-47-like tags today). The mockups' language picker over "Ordo's language list" waits until a language list exists. T2.6 owns Arrangement details.
- **No Arrangement editor exists yet.** T2.6 builds it. Opening an Arrangement shows a focused, read-only Arrangement overview (title, languages, Choirs, sections and Sequence) in the shell's focused-editor frame. That is a real view T2.6 extends, not a placeholder, and it proves the return path.

## Work packages

### WP1: Library store (T2.4a). Design-sensitive: schema, hydration.

- `migrations/0005_library_details.sql` adds:
  - `choir.short_label` and `choir.notes` (both nullable, with not-blank CHECKs);
  - `choir_language (choir_id, language)`;
  - `arrangement.pagination_state` (`'draft' | 'approved' | 'needs_review'`, default `'draft'`).
  - Re-bless `ERD.md`.
- Storage Interface:
  - `library()` returns every Song, Arrangement and Choir with archive state, in one read transaction.
  - `archive_*` / `restore_*` for each of the three kinds.
  - `create_choir` takes the optional details, `edit_choir` updates them, and `set_pagination_state`.
  - Each write is one IMMEDIATE transaction with the T2.1 error shape.
- Domain:
  - `Choir` gains `short_label`, `notes` and `languages`.
  - `SongLibrary::hydrate(songs, arrangements, choirs)` builds the aggregate from stored records and validates the invariants. A stored row that breaks one is a typed error, never a panic.

### WP2: Search, filters, evidence (T2.4b). Design-sensitive: matching semantics. AC4, AC5, AC6 (model), AC9 (model).

`search.rs` provides `LibraryQuery { text, choirs, languages, occasions, include_archived }` and `search(&SongLibrary, &LibraryQuery) -> Vec<SongHit>`:
- The text match is normalized and case-insensitive, the same match key as T2.3 plus diacritic folding for search only. Authored text is never changed.
- Filters are evaluated per Arrangement. Unspecified is its own filter value, never a wildcard.
- Each `SongHit` carries `matching_arrangements` / `total_arrangements` and `evidence`: Title, Alias(text), Attribution, ArrangementTitle, Choir, Language, or Lyric{arrangement, section, line}.
- Ranking puts title and alias first, then the rest (Decision 41). Ties break by title, then id.
- Archived Songs and Arrangements are included only when `include_archived` is set.

### WP3: Songs workspace (T2.4c). GPUI-facing. AC1, AC2, AC3, AC6, AC7, AC9.

- The app opens the `LibraryStore`, and the xtask gate change lands here.
- The Songs list has a search field, filter chips and Include archived. Each result row shows its evidence line and matching/total count.
- The detail pane shows identity and the Arrangements. Matching Arrangements come first; the others stay visible but subdued. Archived items are inspect-only, with a notice.
- The workspace covers the empty, no-match, archived-only and selected states.
- Open Arrangement goes to the focused overview, and Back returns with query, filters, selection and scroll intact.
- `[UI-AUTO]` tests cover each state and the round trip.

### WP4: Choirs workspace (T2.4d). GPUI-facing. AC8.

- List-detail with Add choir (a name-only inline field), details that save as you type, and rename.
- Archive and restore, with Show archived, and the repertoire table.
- Shows **No choirs yet** when there are none.
- `ChoirQuickCreate` is a reusable inline component that checks for duplicates by normalized, case-insensitive name. On a match it offers the existing Choir instead, even an archived one.

### WP5: E2E, lab, ticks (T2.4d). Mechanical.

- **E2E:** seed mixed Songs and Arrangements, then search combined with three Arrangement-scoped filters. Open an Arrangement and return; the query, evidence, selection and scroll are the same. Repeat from every empty-state variant.
- **Lab:** `songs-library-lab` seeds a temporary parish and launches the real shell over it.
- Tick the AC and freeze this plan.
